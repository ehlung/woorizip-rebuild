# 우리.zip 리빌드 계획

## 1. 리빌드 목적과 방향

### 서비스 개요

**우리.zip**은 가족 간의 소통을 영상으로 기록하고 공유하는 **Q&A 기반 가족 아카이빙 서비스**다.

바쁜 일상 속에서 가족 구성원들이 매주 주어진 질문에 영상으로 답변하고, 그 답변을 가족 단위로 모아 시간이 지나도 다시 꺼내볼 수 있는 디지털 아카이브를 만드는 것을 목표로 한다.

### 리빌드 배경

기존 팀 프로젝트는 서비스 아이디어와 핵심 기능의 가능성을 검증했다. 프론트엔드, 백엔드, AI 서버를 각각 로컬에서 연결해 시연 가능한 상태까지 구현했으나, 각 서버를 독립적으로 배포한 뒤에는 환경변수, CORS, 서버 간 URL, AI 서버 접근 경로 문제로 end-to-end 플로우가 안정적으로 동작하지 않았다.

이후 시연을 위해 일부 설정이 로컬 주소 기준으로 임시 고정되었고, 결과적으로 배포 링크 하나로 전체 서비스를 재현하기 어려운 상태가 되었다.

이번 리빌드는 기존 프로젝트를 다시 만드는 것이 아니라, **로컬 시연 중심의 구조를 실제 운영 가능한 서비스 구조로 재설계하는 것**을 목표로 한다. 클라이언트, 서버, AI 전 영역을 하나의 설계 방향 아래에서 다시 구성하고, 각 영역에서 기존 구현이 다루지 못했던 문제를 해결한다.

### 영역별 리빌드 방향

#### 프론트엔드

- 기존 화면을 옮기지 않고, 디자인 시스템을 새로 정의한 뒤 그 위에서 화면을 다시 구성한다.
- 디자인 토큰과 공통 컴포넌트를 먼저 만들고, 화면은 공통 컴포넌트의 조합으로 구현한다.
- 모바일 앱을 먼저 구축하고, 이후 웹 클라이언트를 별도로 만든다. 두 클라이언트는 디자인 토큰, API 클라이언트, 공통 로직을 공유한다.
- 인증, 토큰 갱신, 서버 상태 관리, 업로드, 분석 상태 추적, 에러 처리를 클라이언트 설계 대상으로 다룬다.
- 고령 사용자를 고려한 접근성(글자 크기, 대비, 스크린 리더)을 디자인 시스템 수준에서 반영한다.

#### 백엔드

- 기존과 같은 Spring Boot를 사용하되, 구조와 코드는 새로 설계한다.
- 도메인 중심 구조, 가족 단위 인가, 비동기 처리의 정합성, 멱등성, 테스트, 성능 측정을 다룬다.

#### AI

- 기존 기능을 이식하는 데서 그치지 않고, 단계별 분석 파이프라인으로 재구성한다.
- 모델과 프롬프트를 평가셋으로 비교해 선택 근거를 남기고, 분석 결과를 활용한 의미 검색까지 확장한다.

### 기존 프로젝트에서 이어받을 것

- 가족 Q&A 기반 영상 아카이빙이라는 서비스 아이디어
- 가족 생성, 초대, 주차별 질문, 영상 답변, 아카이브라는 핵심 도메인
- 얼굴 정렬, 썸네일 생성, STT 요약이라는 AI 기능 방향성
- 팀 프로젝트를 통해 검증한 사용자 시나리오와 주요 화면 흐름

### 리빌드에서 해결할 문제

- 웹앱 중심 UX를 모바일 우선 UX로 전환하고, 웹은 별도 클라이언트로 제공
- 디자인 시스템과 공통 컴포넌트 기반으로 화면 일관성과 재사용성 확보
- 배포 환경에서 클라이언트, 백엔드, AI 서버가 함께 동작하도록 구조화
- 영상 업로드와 AI 분석을 분리하고, 그 사이의 데이터 정합성을 보장
- 환경변수, 비밀값, 파일 저장, API 계약, 배포 구조를 명확히 문서화
- 기존 기능 중심 구현을 도메인 중심 구조로 재설계
- AI 기능을 품질을 측정하고 개선할 수 있는 파이프라인으로 전환

### 주요 기술 과제

**프론트엔드**

- 디자인 토큰 정의와 공통 컴포넌트 라이브러리 구축
- 모바일 앱과 웹 클라이언트 간 디자인 토큰, API 클라이언트, 공통 로직 공유
- OpenAPI 기반 타입 안전한 API 연동
- 토큰 저장, 만료 시 자동 갱신, 동시 요청 중 갱신 충돌 처리
- 서버 상태 캐싱, 낙관적 업데이트, 분석 상태 polling
- 대용량 영상 업로드의 진행률 표시와 실패 복구
- 접근성을 고려한 컴포넌트 설계와 컴포넌트/E2E 테스트

**백엔드**

- Transactional Outbox로 DB 저장과 메시지 발행 사이의 정합성 보장
- AI worker 결과를 결과 큐로 받아 DB 소유권을 API 서버로 일원화
- 업로드 완료 등록, 메시지 중복 수신에 대한 멱등성 처리
- 가족 단위 인가, 초대 코드 가입 동시성 처리
- Testcontainers와 LocalStack 기반 통합 테스트, 부하 테스트 기반 성능 개선

**AI**

- 전사, 요약, 썸네일, 임베딩으로 나눈 단계별 비동기 분석 파이프라인
- STT 모델 비교(CER, 처리 시간)와 평가셋 기반 품질 측정
- LLM 제공자 추상화, 프롬프트 버전 관리, 구조화 출력 검증
- 얼굴 검출과 프레임 품질 점수 기반 썸네일 선택
- 임베딩과 pgvector 기반 가족 아카이브 의미 검색

**인프라**

- AWS S3, CloudFront, SQS를 활용한 미디어 중심 아키텍처
- Docker Compose와 LocalStack 기반 재현 가능한 로컬 환경
- 단계별 dev 배포로 end-to-end 동작을 지속적으로 확인

## 2. 이전 서비스 구조 및 구현 범위 정리

### 이전 기술 스택

| 영역       | 기존 스택                                                                |
| ---------- | ------------------------------------------------------------------------ |
| Frontend   | React, Vite, JavaScript, React Router, Tailwind CSS                      |

### 이전 구현 목표

기존 서비스는 다음 기능을 목표로 했다.

- 가족 생성 및 초대 코드 기반 가입
- 주차별 질문 제공
- 사용자의 영상 답변 촬영 및 업로드
- AI 기반 얼굴 정렬 안내
- AI 기반 썸네일 생성
- STT 기반 영상 요약 및 제목 생성
- 가족 구성원별/주차별 영상 아카이브
- 일상 기록
- 쪽지함
- 마이페이지 및 접근성 기능

### 기존 구조의 문제점

#### 배포와 실행 재현성 문제

기존 프로젝트는 로컬 환경에서 프론트엔드, 백엔드, AI 서버를 연결해 시연 가능한 상태까지 구현했다. 그러나 세 서버를 각각 독립적으로 배포한 뒤에는 환경변수, CORS, 서버 간 URL, AI 서버 접근 경로 문제가 발생했고, 배포 환경에서 전체 플로우가 안정적으로 동작하지 않았다.

배포된 프론트 번들에는 `https://woorizip.site` 백엔드 URL 흔적이 있었으나, 현재 해당 서버는 응답하지 않는 상태다. 이후 시연을 위해 일부 설정이 로컬 주소 기준으로 임시 고정되었고, 결과적으로 배포 링크 하나로 전체 서비스를 재현하기 어려운 구조가 되었다.

리빌드에서는 클라이언트, API 서버, AI worker, DB, S3 저장소의 책임을 명확히 나누고, 환경별 설정과 배포 구조를 처음부터 문서화한다. 또한 배포를 마지막 단계에 몰지 않고, 각 단계가 끝날 때마다 dev 환경에 배포해 end-to-end 동작을 확인한다.

#### 모바일 서비스와 웹앱의 불일치

우리.zip의 핵심 경험은 영상 촬영, 가족 알림, 모바일 접근성, 음성 안내에 가깝다. 하지만 기존 구현은 Vite 기반 웹앱이었기 때문에 네이티브 앱에서 기대되는 촬영 경험, 파일 처리, 푸시 알림, 모바일 내비게이션을 충분히 살리기 어려웠다.

리빌드에서는 Expo React Native 기반 모바일 앱을 주 클라이언트로 설계한다. 웹은 모바일 화면을 그대로 옮기지 않고, 큰 화면에서 아카이브를 열람하는 등 웹에 맞는 사용 흐름을 가진 별도 클라이언트로 만든다.

#### 영상 업로드와 AI 분석 구조 문제

기존 구조에서는 영상 업로드 후 백엔드가 AI 서버에 썸네일/STT 분석을 요청하고, 분석이 끝날 때까지 응답을 기다리는 구조에 가까웠다.

이 방식은 다음 문제가 있다.

- AI 분석이 오래 걸리면 사용자 요청이 지연됨
- AI 서버 실패가 영상 업로드 실패로 번질 수 있음
- 여러 사용자가 동시에 업로드하면 백엔드 부하가 커짐
- 분석 상태를 명확히 보여주기 어려움

리빌드에서는 영상 업로드, 답변 등록, AI 분석, 결과 반영을 분리한다. 사용자는 업로드 완료 후 바로 다음 행동을 할 수 있고, AI 결과는 `ANALYZING`, `READY`, `FAILED` 상태로 추적한다.

단, 단순히 비동기로 나누기만 하면 "답변은 저장됐는데 분석 요청이 유실되는" 문제가 새로 생긴다. 리빌드에서는 Transactional Outbox와 멱등한 결과 반영으로 이 문제까지 다룬다.

#### AI 기능의 품질 검증 부재

기존 AI 기능은 동작 여부를 검증하는 수준이었고, STT 정확도, 요약 품질, 처리 시간, 비용을 측정하는 기준이 없었다. 그래서 모델이나 프롬프트를 바꿨을 때 결과가 나아졌는지 판단할 근거도 없었다.

리빌드에서는 평가셋과 지표를 먼저 정하고, 모델/프롬프트 버전을 분석 결과와 함께 기록해 개선 효과를 비교할 수 있게 한다.

#### 보안 및 운영 문제

AI 레포에는 `.env` 파일이 Git에 포함된 흔적이 있고, 서비스 계정 파일과 임시 파일 관리도 정리되어 있지 않았다. 또한 AI 서버는 CORS 전체 허용, API key 요청 전달 등 운영 환경에 적합하지 않은 구조가 있었다.

리빌드에서는 모든 비밀값을 환경변수 또는 secret manager로 분리하고, 레포에는 `.env.example`만 남긴다. API key는 클라이언트 요청으로 전달하지 않고 서버 환경에서만 관리한다. AI 서버는 외부에 직접 노출하지 않고, 클라이언트는 API 서버만 호출한다.

## 3. 새로운 구조 요약

리빌드의 목표 구조는 Expo 모바일 앱과 웹 클라이언트, Spring Boot API 서버, FastAPI AI 서버/worker, PostgreSQL(pgvector), S3/CloudFront/SQS로 구성한다.

- 클라이언트는 API 서버만 호출한다.
- 모바일 앱과 웹은 디자인 토큰, API 클라이언트, 공통 로직 패키지를 공유한다.
- DB는 API 서버만 쓴다. AI worker는 분석 결과를 결과 큐로 보내고, API 서버가 이를 받아 반영한다.
- 분석 요청은 Transactional Outbox를 거쳐 SQS로 발행한다.

상세 아키텍처, 기술 스택 선택 이유, 프론트엔드/백엔드/AI 설계, 처리 흐름, 상태 설계, 도메인 전략은 [아키텍처 문서](./architecture.md)에서 관리한다.

## 4. 단계별 구현 목표

### 1단계. 리빌드 기반 설계 및 모노레포 초기화

목표는 기존 프로젝트를 그대로 옮기는 것이 아니라, 핵심 도메인과 사용자 흐름을 기준으로 새 구조를 잡는 것이다.

주요 작업:

- 모노레포 구조 설계: `apps/mobile`, `apps/web`, `apps/api`, `apps/ai`, `packages/*`, `infra`
- 기존 서비스 기능 목록 정리
- 핵심 도메인 정의: Family, Member, Question, VideoAnswer, Comment, AnalysisJob
- ERD 초안 작성
- 주요 사용자 플로우와 화면 흐름 설계
- API 책임과 AI 책임 분리
- Docker Compose 기반 로컬 개발 환경(PostgreSQL, LocalStack) 구성
- 환경변수, 보안, 배포 전략 초안 정리

완료 기준:

- README와 아키텍처 문서 작성
- ERD와 주요 사용자 플로우 정의
- `docker compose up`으로 로컬 인프라 실행 가능

### 2단계. Spring 백엔드 코어 구축

목표는 클라이언트가 사용할 안정적인 서비스 API와, 이후 기능을 얹을 수 있는 백엔드 기반을 만드는 것이다.

주요 작업:

- Spring Boot 3, Java 21, Gradle 프로젝트 구성
- 도메인별 패키지 구조 설계
- Spring Data JPA, QueryDSL, Flyway 설정
- Spring Security와 JWT 인증(access/refresh token, refresh rotation)
- 가족 멤버십 기반 인가
- 가족 생성/초대 코드/가입 API (가입 동시성 처리 포함)
- 주차 질문 API
- 공통 에러 응답 구조
- springdoc-openapi 기반 API 문서화
- JUnit5, Testcontainers 기반 테스트
- GitHub Actions CI(빌드, 테스트)

완료 기준:

- 인증된 사용자 기준으로 가족 데이터가 분리됨
- 다른 가족의 리소스 접근 시 거부됨을 테스트로 검증
- OpenAPI 스펙이 자동 생성됨
- Actuator health check 제공
- CI에서 통합 테스트까지 통과

### 3단계. 디자인 시스템 및 모바일 앱 기반 구축

목표는 기존 화면을 옮기는 것이 아니라, 디자인 시스템을 먼저 세우고 그 위에서 모바일 앱의 구조와 공통 기반을 만드는 것이다.

주요 작업:

- 디자인 시스템 정의: 색상, 타이포그래피, 간격, radius, 그림자, 모션 토큰
- 접근성 기준 반영: 최소 글자 크기, 대비, 터치 영역, 글자 크기 확대 대응
- `packages/design-tokens`로 토큰을 플랫폼 중립적으로 관리
- 공통 컴포넌트 구축: Button, TextField, Card, Header, Avatar, Badge, Modal, Toast, 빈/로딩/에러 상태
- Storybook으로 컴포넌트 문서화
- Expo 앱 초기 세팅, TypeScript, 라우팅, 내비게이션 구조
- `packages/api-client`: OpenAPI 스펙 기반 TypeScript 클라이언트 자동 생성
- 인증 흐름: 토큰 보안 저장, 만료 시 자동 갱신, 동시 요청 중 갱신 요청 단일화, 갱신 실패 시 로그아웃
- TanStack Query 기반 서버 상태 관리, 공통 에러 처리
- 로그인/온보딩/가족 생성·가입/질문 조회 화면 구현
- 카메라 촬영 화면 프로토타입

완료 기준:

- 화면이 공통 컴포넌트 조합으로 구성되고, 화면 코드에 스타일 값이 직접 들어가지 않음
- 앱에서 로그인, 가족 생성/가입, 질문 조회가 실제 API와 연결되어 동작

- 주요 공통 컴포넌트에 대한 컴포넌트 테스트 작성

### 4단계. S3 기반 영상 업로드 구현

목표는 앱에서 촬영한 영상을 안정적으로 저장하고, DB에는 메타데이터만 관리하는 구조를 만든다.

주요 작업:

- S3 버킷 구성 (로컬은 LocalStack)
- API 서버에서 presigned upload URL 발급
- 앱에서 S3 직접 업로드, 진행률 표시, 실패 시 재시도
- 업로드 완료 등록 API (멱등 처리)
- 영상 상태 관리: `UPLOADING`, `UPLOADED`, `ANALYZING`, `READY`, `FAILED`
- 영상 조회 URL 생성
- CloudFront 도입 준비

완료 기준:

- 앱에서 촬영한 영상이 S3에 저장됨
- DB에는 영상 object key와 답변 메타데이터가 저장됨
- 업로드 중 네트워크가 끊겨도 재시도로 완료 가능
- 업로드 완료 요청이 중복으로 와도 상태가 한 번만 전이됨을 테스트로 검증

### 5단계. 비동기 AI 분석 파이프라인 구축

목표는 영상 업로드와 AI 분석을 분리하되, 분석 요청 유실과 중복 처리가 없는 비동기 처리 구조를 만든다.

주요 작업:

- Transactional Outbox: 답변 저장과 분석 이벤트 저장을 하나의 트랜잭션으로 처리
- Outbox relay가 SQS `analysis-jobs` 큐로 발행
- FastAPI 기반 AI worker 구성, SQS 메시지 수신
- 분석 단계 구현: `TRANSCRIBE -> SUMMARIZE -> THUMBNAIL -> EMBED`
  - 전사: faster-whisper
  - 요약/제목: LLM 제공자 추상화 계층을 통해 호출
  - 썸네일: 기존 로직 이식 후 정리
- AI worker는 결과를 SQS `analysis-results` 큐로 발행
- API 서버가 결과 큐를 소비해 멱등하게 DB 반영
- 재시도, DLQ, `FAILED` 처리와 수동 재분석 API
- 얼굴 정렬 가이드 API (API 서버 경유)
- 앱에서 분석 상태 polling과 상태별 UI

완료 기준:

- 영상 업로드 후 상태가 `ANALYZING -> READY`로 전이됨
- 앱에서 썸네일, 제목, 요약을 확인 가능
- 실패 시 `FAILED` 상태와 fallback UI 표시
- relay 또는 worker를 중간에 강제 종료해도 분석 요청이 유실되지 않음을 테스트로 검증
- 같은 결과 메시지가 두 번 와도 한 번만 반영됨을 테스트로 검증

### 6단계. 가족 아카이브 경험 완성

목표는 우리.zip의 핵심 가치인 가족 기록 저장과 재방문 경험을 완성하고, 서비스 전체 플로우를 end-to-end로 연결한다.

주요 작업:

- 주차별 영상 아카이브
- 가족 구성원별 영상 모아보기
- 영상 상세 보기
- 댓글/반응 (낙관적 업데이트)
- 답변 참여 상태 표시
- 긴 목록 가상화, 썸네일 캐싱
- 아카이브 조회 쿼리 최적화(N+1 제거, 인덱스, 커서 페이지네이션)
- 빈 상태, 로딩 상태, 실패 상태 정리
- 핵심 플로우 E2E 테스트

완료 기준:

- 가족 구성원이 남긴 영상 답변을 주차별/구성원별로 탐색 가능
- 영상 상세에서 요약, 썸네일, 댓글 확인 가능
- 서비스의 핵심 플로우가 dev 환경에서 end-to-end로 동작
- 가입부터 답변 업로드, 아카이브 조회까지 E2E 테스트 통과

### 7단계. AI 품질 고도화 및 의미 검색

목표는 AI 기능을 "동작하는 수준"에서 "측정하고 개선할 수 있는 수준"으로 끌어올리고, 아카이브 의미 검색을 추가한다.

- 썸네일 선택 개선: 얼굴 검출, 선명도, 눈 뜸/표정 점수 기반 프레임 선택

AI는 평가셋 기반으로 STT와 요약 품질을 측정하고 임베딩 기반 의미 검색까지 확장해, 실제 배포 환경에서 동작하는 가족 영상 아카이빙 서비스를 만든다.

## Assumptions

- 기존 팀 레포는 원본으로 보존하고, 리빌드는 별도 레포에서 진행한다.
- 기존 코드는 그대로 복사하지 않고, 도메인/기능/AI 로직을 참고해 새 구조로 재구성한다. 백엔드는 기존과 같은 Spring Boot를 쓰지만 구조와 코드는 새로 작성한다.
- 디자인은 기존 화면을 참고만 하고, 디자인 시스템부터 새로 정의한다.
- 모바일 앱을 먼저 완성하고, 웹 클라이언트는 이후 별도로 구축한다. UI 컴포넌트는 플랫폼별로 구현하되 토큰, API 클라이언트, 공통 로직은 공유한다.
- 백엔드는 Spring Boot 3, Java 21, Spring Data JPA, Flyway를 사용한다.
- DB는 pgvector 사용을 위해 기존 MySQL 대신 PostgreSQL을 사용한다.
- LLM은 특정 제공자에 종속되지 않도록 추상화 계층을 두고, 실제 제공자는 평가 결과를 보고 결정한다.
- 의미 검색은 필수 범위, 질문 추천은 핵심 플로우 완성 이후 후순위로 진행한다.
- 반려동물 숏츠와 쪽지함은 핵심 플로우 완성 이후 후순위로 진행한다.
- 각 단계가 끝날 때마다 dev 환경에 배포해 end-to-end 동작을 확인한다.
- 기존 `woorizip.site` 도메인의 재사용 여부는 소유권과 팀 프로젝트와의 경계를 확인한 뒤 결정한다.
- AWS는 S3, CloudFront, SQS를 우선 도입하고, 컴퓨팅(App Runner/ECS)과 RDS 범위는 배포 단계에서 확정한다.
