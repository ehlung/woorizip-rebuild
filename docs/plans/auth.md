# 가입·로그인 작업 계획

0단계의 이메일 가입, 로그인, 토큰 재발급, 로그아웃, 비밀번호 재설정을 만드는 계획이다. 작업하면서 정한 것과 계획에서 바뀐 것을 날짜와 함께 이 문서에 적는다.

근거 문서: [ADR 0009](../adr/0009-auth-token.md)(인증 토큰), [ADR 0018](../adr/0018-email-delivery.md)(메일 발송), [03-architecture.md](../03-architecture.md) 8장(인증, 가입 이메일 인증), [user-flows.md](../user-flows.md) A·B 흐름, [04-evaluation.md](../04-evaluation.md)의 A-37~48, A-83~88

## 만들 기능

| 기능 | 서버가 하는 일 |
| --- | --- |
| 가입 이메일 인증 | 6자리 코드를 해시로 저장하고 메일로 보낸다. 맞으면 짧은 수명의 가입 확인 값을 발급한다 |
| 가입 | 가입 확인 값을 검증하고 계정을 만든다(이름, 화면 크기, 동의). access token과 refresh token을 발급한다 |
| 로그인 | BCrypt로 비밀번호를 비교한다. 실패 응답으로 가입 여부를 알 수 없게 한다 |
| 토큰 재발급 | access token은 15분. refresh token은 쓸 때마다 바꾸고, 이미 쓴 것이 오면 그 사용자의 refresh token을 모두 폐기한다. 30일 동안 안 쓰면 만료, 최대 1년 |
| 로그아웃 | 그 기기의 refresh token을 폐기한다 |
| 비밀번호 재설정 | 코드를 확인하고 비밀번호를 바꾼 뒤 모든 refresh token을 폐기한다 |
| 메일 발송 | 발송 작업을 DB에 저장하고 커밋 직후 보낸다. 실패하면 스케줄러가 다시 보낸다. 로컬과 테스트는 가짜 발송을 쓴다 |

이번에 하지 않는 것: 앱 화면, 소셜 로그인(1단계), 회원 탈퇴, 실제 SES 발송

## PR 2 설계: 메일 발송과 가입

### API

| 요청 | 하는 일 | 응답 |
| --- | --- | --- |
| `POST /auth/signup/email-code` `{email}` | 가입 인증 코드를 메일로 보낸다. 이미 가입된 이메일이면 코드 대신 안내 메일을 보낸다 | 어느 경우든 202. 횟수를 넘으면 429 `TOO_MANY_REQUESTS` |
| `POST /auth/signup/email-code/verify` `{email, code}` | 코드를 확인하고 가입 확인 값을 발급한다 | 200 `{signupToken, expiresAt}`. 틀리면 `EMAIL_CODE_INVALID`, 만료·5회 틀림·없음은 `EMAIL_CODE_EXPIRED` |
| `POST /auth/signup` `{signupToken, password, name, screenSize, consents}` | 계정을 만들고 동의를 기록한다 | 201 `{userId, accessToken, accessTokenExpiresAt}`. 확인 값이 없거나 만료되면 `SIGNUP_TOKEN_INVALID` |

### 표 (V2 마이그레이션)

| 표 | 내용 |
| --- | --- |
| `email_codes` | 목적(가입, 비밀번호 재설정), 이메일, 코드 해시, 틀린 횟수, 만료, 사용 시각 |
| `signup_tickets` | 이메일, 가입 확인 값 해시, 만료, 사용 시각 |
| `mail_jobs` | 종류, 받는 사람, 제목, 본문, 상태, 시도 횟수, 다음 시도 시각, 만료 |
| `user_consents` | 사용자, 동의 종류, 약관 버전, 동의 시각 |

### 메일 발송

요청 트랜잭션에서 `mail_jobs`에 저장하고, 커밋 직후 바로 보낸다. 실패하면 스케줄러가 `FOR UPDATE SKIP LOCKED`로 꺼내 다시 보낸다(03-architecture 7장의 푸시 알림과 같은 방식). 로컬과 테스트는 가짜 발송을 쓰고, 가짜 발송은 `local`, `test` 프로필에서만 등록된다(ADR 0005의 "개발용 장치는 운영에서 켤 수 없게").

## PR 3 설계: 로그인과 토큰

### API

| 요청 | 하는 일 | 응답 |
| --- | --- | --- |
| `POST /auth/login` `{email, password}` | 비밀번호를 확인하고 토큰을 발급한다 | 200 토큰. 틀리면 이메일이 없든 비밀번호가 틀리든 401 `LOGIN_FAILED`. 잠겨 있으면 429 `TOO_MANY_REQUESTS` |
| `POST /auth/token/refresh` `{refreshToken}` | refresh token을 새것으로 바꾸고 access token을 새로 발급한다 | 200 토큰. 쓸 수 없으면 401 `REFRESH_TOKEN_INVALID` |
| `POST /auth/logout` `{refreshToken}` | 그 기기의 refresh token을 폐기한다 | 204. 이미 폐기됐거나 없는 토큰이어도 204 |
| `POST /auth/signup` | PR 2와 같고, 응답에 refresh token을 더한다 | 201 |

토큰 응답: `{userId, accessToken, accessTokenExpiresAt, refreshToken, refreshTokenExpiresAt}`

### 표 (V3 마이그레이션)

| 표 | 내용 |
| --- | --- |
| `refresh_tokens` | 사용자, 세션 ID(한 번 로그인한 기기에서 이어지는 토큰 묶음), 토큰 해시, 세션 시작 시각, 만료 시각, 바꾼 시각(rotation), 폐기 시각 |
| `login_failures` | 이메일, 연속 실패 횟수, 잠금이 풀리는 시각 |

## 정한 것

| 날짜 | 내용 | 이유 |
| --- | --- | --- |
| 2026-11-25 | JWT 서명은 HS256 | 토큰을 발급하고 검증하는 곳이 모두 API 서버라 공개키 방식이 필요 없다. 키는 32바이트 이상(RFC 7518 3.2) |
| 2026-11-25 | 횟수 제한: 같은 이메일로 코드 요청은 1분에 1번, 하루 10번. 같은 계정에 로그인이 5번 연속 실패하면 실패할 때마다 기다리는 시간을 늘린다. 기록은 DB에 둔다 | 문서에는 "제한을 둔다"만 있어 숫자를 정했다. 공식 기준에서 가져온 숫자가 아니라 판단이다 |
| 2026-11-25 | 메일은 가짜 발송까지만. 실제 SES 발송은 도메인을 정한 뒤(ADR 0017) | SES 도메인 인증에는 소유한 도메인의 DNS 설정이 필요하다 |
| 2026-11-25 | 오류 응답은 RFC 9457 ProblemDetail에 `code`를 더한 형식 | Spring이 기본으로 지원하고, Spring이 직접 만드는 오류(404, 405 등)도 같은 형식으로 나온다 |
| 2026-11-25 | 로컬과 테스트의 서명 키는 켤 때마다 무작위로 만든다(`${random.value}` 두 개를 이어 붙임) | 설정 항목은 운영과 같고 값만 다르다(ADR 0014). `${random.value}` 하나는 128비트라 둘을 잇는다 |
| 2026-11-26 | 비밀번호는 8자 이상 64자 이하, UTF-8로 72바이트 이하. 문자 종류 규칙은 두지 않고, 띄어쓰기와 한글을 받는다 | 사용자 결정. 연세 많은 사용자의 입력 부담을 줄인다. NIST SP 800-63B-4는 비밀번호만으로 로그인하면 15자 이상을 요구하므로(SHALL) 그 기준에는 못 미친다. 문자 종류 규칙 금지, 64자 이상 허용, 유니코드 허용은 NIST를 따른다. 72바이트 제한은 BCrypt 때문이다. Spring Security 7.1.3의 BCrypt는 72바이트를 넘으면 예외를 던지는 것을 직접 돌려 확인했다(한글은 24자까지) |
| 2026-11-26 | 약관 4개(서비스 이용, 개인정보 처리, 영상·음성의 외부 AI 전송, 14세 이상)는 모두 필수 | 사용자 결정. 0단계는 지인 대상 테스트 배포이고 AI 정리가 핵심 기능이라, 동의하지 않은 사용자의 분석을 건너뛰는 경로를 만들지 않는다. 외부 AI 전송을 선택으로 둬야 하는지 법적 요건은 확인하지 못했고, 정식 출시 전에 다시 확인한다 |
| 2026-11-26 | 약관 버전은 아직 약관 문서가 없어 `v0`으로 기록한다 | 약관을 쓰면 버전을 올리고, 동의 기록은 버전별로 남는다 |
| 2026-11-26 | 가입 확인 값은 30분 뒤 만료 | 코드 확인 뒤 비밀번호, 이름, 화면 크기를 입력할 시간이다. 판단으로 정한 값이다 |
| 2026-11-26 | 코드 요청 횟수는 가입 메일(코드, 이미 가입 안내)을 합쳐 같은 이메일당 센다 | 이미 가입된 이메일에도 같은 제한을 걸어야 응답이나 제한으로 가입 여부를 알 수 없고, 남의 메일함에 안내 메일을 쏟아부을 수 없다 |
| 2026-11-26 | 메일 본문(코드 포함)은 `mail_jobs`에 저장했다가 보낸 뒤나 만료되면 지운다 | 재시도하려면 본문이 있어야 한다. ADR 0009의 "DB에는 해시만"과 다르지만, 코드는 10분이면 만료되고 보내면 바로 지운다 |
| 2026-11-26 | 같은 이메일의 코드 요청은 PostgreSQL advisory lock(`pg_advisory_xact_lock`)으로 한 번에 하나씩 처리한다 | 잠그지 않으면 동시에 온 요청이 모두 횟수 제한을 통과해 메일이 두 통 나갔다(잠금을 뺀 채 테스트를 3번 돌려 3번 모두 확인). 잠금은 트랜잭션이 끝나면 자동으로 풀리고, 서버가 여러 대여도 DB에서 순서가 맞는다 |
| 2026-11-26 | API 명세의 모든 API에 오류 응답(`ApiProblem`, 오류 코드 목록 포함)을 넣는다 | 앱용 클라이언트가 오류 코드를 타입으로 알 수 있어야 한다. 처음에는 앱 작업 전으로 미뤘으나, 명세와 클라이언트 생성은 PR 1이 맡은 일이라 PR 2에서 바로 넣었다 |
| 2026-11-26 | refresh token은 이미 바꾼(rotation) 토큰이 다시 오면 그 사용자의 refresh token을 모두 폐기하고, 로그아웃으로 폐기한 토큰이 오면 거부만 한다 | 바꾼 토큰이 다시 오는 것은 토큰을 훔친 쪽과 원래 사용자가 같은 토큰을 쓴 경우라 모두 폐기한다(ADR 0009, RFC 9700). 로그아웃한 토큰은 앱이 오래된 토큰으로 한 번 더 요청한 경우가 많아, 다른 기기 로그인까지 끊지 않는다 |
| 2026-11-26 | refresh token 만료: 발급할 때마다 그 시각부터 30일, 단 세션을 시작한 뒤 1년을 넘지 않는다 | ADR 0009의 "마지막 사용 후 30일, 처음 로그인한 뒤 최대 1년" |
| 2026-11-26 | 로그인 실패 제한: 같은 이메일로 5번 연속 실패하면 1분 잠그고, 그 뒤 실패할 때마다 잠금 시간을 2배로 늘린다(최대 15분). 성공하면 초기화한다 | "5번 연속 실패 후 실패마다 대기 시간 증가"(PR 1 때 정함)의 숫자를 정했다. 1분, 2배, 15분은 판단으로 정한 값이다 |
| 2026-11-26 | 로그인 실패 횟수는 가입 여부와 관계없이 이메일로 센다. 없는 이메일도 가짜 해시로 비밀번호를 한 번 비교한다 | 잠금이나 응답 시간으로 가입 여부를 알 수 없게 한다(A-47). 가짜 해시 비교는 Spring Security `DaoAuthenticationProvider`의 방식이다(7.1.3 소스의 `mitigateAgainstTimingAttack`) |
| 2026-11-26 | 로그아웃은 access token 없이 refresh token만으로 한다 | access token이 이미 만료된 상태에서도 로그아웃할 수 있어야 한다 |
| 2026-11-26 | 서버 시계는 마이크로초 단위로 끊는다(`Clock.tick`) | PostgreSQL timestamptz의 해상도는 1마이크로초다. Linux CI에서 나노초가 있는 시각으로 만료 시각을 저장하자, 저장된 값이 계산한 값보다 뒤가 되어 만료 시각과 같은 순간에도 코드와 가입 확인 값이 통과했다. 로컬(macOS)은 `Instant.now()`가 마이크로초 단위라 드러나지 않았고, 시작 시각에 나노초를 붙여 로컬에서 같은 실패를 재현한 뒤 고쳤다 |
| 2026-11-26 | 메일 재시도는 30초, 1분, 2분, 4분 뒤. 코드가 만료되면 더 보내지 않는다 | 만료된 코드를 보내도 쓸 수 없다. 간격은 판단으로 정한 값이다 |
| 2026-11-26 | npm은 Dependabot 새 버전 PR을 끄고(`open-pull-requests-limit: 0`) 보안 업데이트만 받는다. 저장소의 Dependabot 보안 알림과 자동 보안 업데이트를 켰다 | 앱(Expo) 패키지는 SDK가 기대하는 버전에 맞춰야 해서, SDK와 상관없는 최신 버전 PR은 오히려 어긋난다 |
