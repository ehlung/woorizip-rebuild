# 0004. 분석 실패 상태와 재시도

- 상태: 채택
- 날짜: 2026-11-20
- 관련 문제: P-07, P-08, P-09, P-10 ([01-legacy-analysis.md](../01-legacy-analysis.md))

## 맥락

기존 구현은 실패를 다루는 방법이 없었다.

- 썸네일 단계가 실패하면 업로드 전체가 실패했다 (P-07)
- 실패하면 남은 파일을 정리하지 않았고, 다시 시도할 방법이 없었다 (P-08)
- 일시적인 오류를 확정된 결과로 저장했다. 반려동물 판별이 실패하면 "반려동물 아님"으로 영구 저장됐다 (P-09)
- 앱은 업로드 실패를 복구할 수 없었고, 새로고침하면 녹화본이 사라졌다 (P-10)

[ADR 0002](0002-async-analysis.md)에서 분석을 작업으로 분리하고 lease를 두었고, [ADR 0003](0003-video-upload.md)에서 앱이 업로드 완료를 알리기로 했다. 두 결정에서 넘어온 다음 문제를 여기서 정한다.

- 분석이 실패하면 몇 번, 어떤 간격으로 다시 시도하는가
- 끝내 실패하면 답변은 어떤 상태가 되는가
- lease가 만료된 뒤 원래 워커의 결과가 늦게 도착하면 어떻게 하는가
- 앱이 완료 알림을 여러 번 보내거나, 업로드 자체가 실패하면 어떻게 하는가

## 판단 기준

1. 어느 단계가 실패해도 사용자의 기록(영상)을 잃지 않는다
2. 일시적인 실패를 확정된 결과로 남기지 않는다
3. 같은 결과가 두 번 반영되거나, 같은 답변이 두 번 생기지 않는다
4. 실패했다는 사실과 할 수 있는 일을 사용자가 알 수 있다
5. 외부 AI API에 과부하가 걸렸을 때 재시도가 부하를 키우지 않는다

## 후보

### 재시도 방식

- **재시도 없음**: 한 번 실패하면 바로 실패 처리한다. 일시적인 오류에도 기록이 기본값으로 남는다(기준 2).
- **즉시 재시도**: 실패하자마자 다시 시도한다. 외부 API가 과부하일 때 부하를 키운다(기준 5).
- **간격을 늘려 재시도 (exponential backoff)**: 실패할 때마다 기다리는 시간을 늘린다. 일시적인 장애가 풀릴 시간을 주고 부하를 키우지 않는다.

### 끝내 실패한 답변

- **답변을 만들지 않음 (기존)**: 영상이 S3에 있는데도 사용자는 처음부터 다시 올려야 한다(기준 1).
- **기본값으로 공개**: 영상은 재생할 수 있게 두고, 제목과 썸네일을 기본값으로 채운다. 작성자가 직접 고칠 수 있다.

## 결정

### 1. 실패를 두 종류로 나눈다

| 종류 | 예 | 처리 |
| --- | --- | --- |
| 일시적 실패 | 외부 AI API의 과부하나 일시 오류, 네트워크 끊김, 워커가 멈춰 lease 만료 | 간격을 늘려 재시도 (exponential backoff) |
| 영구 실패 | 영상 파일 손상, 지원하지 않는 형식 | 재시도하지 않고 바로 실패 처리 |

- 워커는 실패를 보고할 때 종류를 함께 보낸다. 종류를 알 수 없는 오류는 일시적 실패로 본다.
- lease 만료도 시도 한 번으로 센다.
- 재시도는 첫 시도 후 최대 3회, 각각 1분, 5분, 15분 뒤에 한다.
- 일시적 실패는 재시도가 모두 끝나기 전까지 결과로 저장하지 않는다(P-09).

### 2. 끝내 실패해도 답변은 남긴다

영상은 이미 S3에 있으므로 답변을 살려 둔다. 이 방향은 [user-flows.md](../user-flows.md)의 흐름 B와 같다.

- 영상은 재생할 수 있다.
- 제목은 질문 문구로, 썸네일은 기본 이미지나 영상의 첫 장면으로 채운다.
- 일부 단계만 성공했다면(예: 썸네일은 성공, 요약은 실패) 성공한 결과는 반영한다.
- 작성자는 0단계 기능인 AI 제목·요약 직접 수정으로 내용을 채울 수 있다.
- 작성자에게 "AI 정리가 안 됐어요, 직접 적어 주세요" 푸시 알림을 보낸다. 분석 실패 알림을 0단계에 추가한다.
- 작성자가 다시 분석을 요청하는 버튼은 1단계로 둔다. 0단계에서는 자동 재시도와 직접 수정으로 충분하다고 본다.

### 3. 늦게 도착한 결과는 시도 번호로 거른다 (fencing token)

워커 A가 멈춘 것으로 보고 lease를 만료시켜 워커 B에게 넘겼는데, A가 뒤늦게 결과를 보내는 경우가 있다. 그대로 받으면 결과가 두 번 반영된다.

- 작업을 워커에 넘길 때마다 시도 번호를 하나씩 올려 함께 넘긴다.
- 결과를 받을 때 현재 시도 번호와 같은지 확인하고, 지난 시도의 결과는 버린다.
- 사용자가 다시 찍어 답변의 영상이 바뀐 경우에도, 이전 영상의 분석 결과는 같은 방식으로 버린다.

### 4. 앱의 업로드 실패와 완료 알림 중복

- 업로드가 실패하면 녹화본을 기기에 남겨 두고 "다시 올리기"를 보여준다. 서버가 완료를 확인하기 전까지 녹화본을 지우지 않는다(P-10).
- 완료 알림은 업로드 세션 단위로 중복을 막는다. 같은 세션으로 여러 번 알려도 답변과 분석 작업은 하나만 생긴다.
- 완료 알림이 오지 않은 파일은 S3 수명 주기 규칙으로 삭제한다([ADR 0003](0003-video-upload.md)).

### 5. 다시 찍기

다시 찍기는 기존 답변의 영상을 교체한다. 연세가 많은 사용자는 여러 번 다시 찍을 수 있으므로, 사용자를 막지 않으면서 비용과 비정상 반복을 줄인다.

- 다시 찍으면 이전 영상의 대기 중인 분석 작업을 취소한다. 여러 번 찍어도 실제로 분석되는 것은 마지막 영상이다. 이미 처리 중인 작업의 결과는 3번의 시도 번호 확인으로 버린다.
- 답변 하나당 다시 찍기는 하루 20회로 제한한다. 일반 사용자가 걸리지 않을 만큼 넉넉하게 두고, 앱 오류로 업로드가 반복되는 것 같은 비정상 상황만 막는다.
- 1차 피드백에서 다시 찍기 횟수 분포를 보고 제한값을 조정한다.

### 버린 후보

- 재시도 없음은 일시적인 오류에도 기록이 기본값으로 남아 기준 2를 만족하지 못한다.
- 즉시 재시도는 외부 API 과부하 상황에서 부하를 키워 기준 5를 만족하지 못한다.
- 실패 시 답변을 만들지 않는 기존 방식은 영상이 저장돼 있는데도 사용자에게 다시 올리게 해 기준 1을 만족하지 못한다.

## 결과

- 얻는 것:
  - 분석이 실패해도 영상과 답변이 남는다.
  - 일시적인 장애는 재시도로 회복되고, 영구적인 오류 데이터로 남지 않는다.
  - 결과가 두 번 반영되거나 답변이 중복되지 않는다.
- 잃는 것:
  - 재시도가 모두 실패하면 결과가 나오기까지 최대 20분 이상 걸린다.
  - 작업에 시도 번호, 재시도 예정 시각, 실패 종류 같은 상태가 늘어난다.
- 후속 작업:

  - [03-architecture.md](../03-architecture.md): 답변과 분석 작업의 상태 전이
  - 운영 중 재시도 횟수와 간격이 맞는지 확인하고 조정

## 검증

assertion:

- 썸네일 단계가 실패해도 업로드는 성공하고, 답변은 영상을 재생할 수 있는 상태로 남는다.
- 일시적 실패는 최대 3회 재시도하고, 그 전에는 실패 결과를 저장하지 않는다.
- 영구 실패는 재시도하지 않고 바로 실패 처리한다.
- lease가 만료된 뒤 지난 시도의 결과가 도착하면 반영하지 않는다.
- 다시 찍은 답변에 이전 영상의 분석 결과가 반영되지 않는다.
- 같은 업로드 세션으로 완료 알림을 여러 번 보내도 답변과 분석 작업은 하나만 생긴다.
- 업로드가 실패해도 녹화본은 기기에 남고, 다시 올릴 수 있다.
- 다시 찍으면 이전 영상의 대기 중인 분석 작업이 취소되고, 마지막 영상만 분석된다.
- 답변 하나당 하루 21번째 다시 찍기는 거부된다.
- 분석이 끝내 실패하면 작성자에게 푸시 알림이 간다.

지표:

- 분석 성공률, 재시도 후 성공률
- 실패 종류별 비율
- 기본값으로 공개된 답변 중 작성자가 직접 고친 비율
- 답변당 다시 찍기 횟수 분포
