# 0005. 서비스 간 통신과 AI 서버 보호

- 상태: 제안 (구체적인 인증 방식은 배포 형태 결정 후 확정)
- 날짜: 2026-11-20
- 관련 문제: P-21, 01의 4장 ([01-legacy-analysis.md](../01-legacy-analysis.md))

## 맥락

기존 AI 서버는 인터넷에 공인 IP로 열려 있었고, 인증 없이 모든 출처를 허용했으며, 암호화하지 않은 HTTP로 통신했다. Gemini API 키는 BE가 요청마다 넘겨줬다. 누구나 AI 서버를 호출해 외부 AI 비용을 발생시킬 수 있었다(P-21).

기존 프로젝트에서는 AWS 키, JWT 서명 키, DB 비밀번호 같은 오래 사는 비밀값이 공개 저장소에 남았다(01의 4장). 서비스 간 인증에 오래 사는 비밀값을 새로 만들면 같은 위험이 다시 생긴다.

앞선 결정으로 상당 부분은 이미 풀렸다.

| 기존 문제 | 현재 상태 |
| --- | --- |
| AI 서버가 인터넷에 열려 있음 | AI 워커가 BE에 먼저 요청만 보낸다. AI 서버에 열린 포트가 없다 ([ADR 0002](0002-async-analysis.md)) |
| 영상을 서버끼리 주고받음 | AI 워커가 BE가 발급한 presigned URL로 S3에서 직접 받는다 ([ADR 0003](0003-video-upload.md)) |
| Gemini API 키를 요청으로 넘겨받음 | AI 서버가 자기 환경 설정으로만 갖는다. 키 관리 방식은 ADR 0014에서 정한다 |
| 누구나 AI 비용을 발생시킬 수 있음 | 분석 작업은 로그인한 가족 구성원이 답변을 올릴 때만 생긴다. 다시 찍기에는 상한이 있다 ([ADR 0004](0004-failure-and-retry.md)) |

남은 문제는 BE의 내부 API(작업 요청, 결과 보고)를 지키는 것이다. 누군가 내부 API를 부를 수 있으면 다른 가족의 작업을 가져가거나 가짜 분석 결과를 넣을 수 있다.

## 판단 기준

1. 서비스 간 인증에 오래 사는 비밀값을 쓰지 않는다
2. 비밀값이 요청마다 네트워크로 오가지 않는다
3. 1인 운영으로 관리할 수 있다
4. 로컬 개발 환경에서도 같은 구조로 실행할 수 있다
5. 한 가지 장치가 뚫려도 다른 장치가 막는다

## 후보

### A. 공유 비밀 토큰

BE와 워커만 아는 긴 토큰을 요청 헤더에 넣는다.

- 장점: 가장 단순하다(기준 3). 외부 서비스의 API 키나 웹훅 서명용 비밀값처럼 실무에서 흔히 쓴다.
- 단점: 토큰이 요청마다 오가 로그에 남거나 가로채일 수 있다(기준 2). 직접 바꾸기 전까지 영구히 유효하다(기준 1). 기존 프로젝트의 비밀값 유출과 같은 종류의 위험이다.

### B. mTLS

BE와 워커가 서로 인증서를 확인하는 암호화 연결을 쓴다.

- 장점: 개인 키가 네트워크로 오가지 않는다(기준 2). 인증과 암호화를 함께 해결한다.
- 단점: 인증서 발급, 갱신, 배포를 직접 관리해야 한다(기준 3). 갱신을 자동화하지 않고 유효기간을 길게 잡으면 결국 오래 사는 비밀값이 된다(기준 1).

### C. 클라우드 권한 (예: AWS IAM 역할)

워커가 클라우드에서 받은 임시 자격 증명으로 자신의 역할을 증명한다. 예를 들어 워커가 AWS 신원 확인 요청에 서명해 BE에 보내고 BE가 AWS에 확인하는 방식, 또는 작업 전달 통로를 IAM으로 보호되는 큐로 두는 방식이 있다.

- 장점: 클라우드가 몇 시간짜리 임시 자격 증명을 자동으로 교체해, 오래 사는 비밀값이 없다(기준 1). 서명만 오가고 비밀값은 오가지 않는다(기준 2).
- 단점: 배포 환경에 묶인다. 로컬 개발에서 흉내 내기 번거롭다(기준 4). 구체적인 구현 모양이 배포 형태에 따라 달라진다.

## 결정 (제안)

다음 원칙을 정하고, 구체적인 인증 방식은 배포 형태를 정한 뒤 확정한다.

1. **서비스 간 인증에 오래 사는 비밀값을 쓰지 않는다.** C(클라우드 권한)를 우선 후보로 하고, 배포 환경에서 C를 쓰기 어려우면 B(mTLS)를 갱신 자동화와 함께 검토한다. A는 기존 비밀값 유출 문제를 다시 만들기 때문에 쓰지 않는다.
2. **내부 API는 공개 API와 경로를 분리하고, 외부에서 들어오는 길에서 막는다.** 서버가 같은 사설망에 있으면 사설 주소로만 연다.
3. **사설망 밖을 지나는 통신은 HTTPS로 보낸다.**
4. **로컬 개발용 인증 우회는 운영 설정에서 켜질 수 없게 한다.** 기존 프로젝트에는 비밀번호 없이 토큰을 발급하는 데모용 코드가 로컬에 남아 있었다. 개발 편의 장치는 운영 빌드나 설정에서 활성화할 수 없는 구조로 둔다.

이 ADR은 다음 결정을 내린 뒤 "채택"으로 바꾼다.

- ADR 0012: AI 제공자 선택. STT와 요약을 외부 API로 쓰면 AI 워커가 가벼워지고, 직접 모델을 돌리면 별도의 큰 서버가 필요해 배포 형태가 달라진다.
- ADR 0017: 배포 형태. 서버를 한 대로 둘지 나눌지, 어느 클라우드에서 실행할지에 따라 C의 구현 모양이 정해진다.

## 결과

- 얻는 것: AI 서버에 열린 포트가 없고, 서비스 간 인증에 오래 사는 비밀값이 생기지 않는다.
- 잃는 것: 구체적인 인증 방식이 배포 형태에 의존한다. 로컬 개발 환경을 따로 준비해야 한다.
- 후속 작업: 0012, 0017을 정한 뒤 이 ADR을 확정한다.

## 검증

assertion:

- 외부에서 내부 API 경로를 호출하면 차단된다.
- 인증되지 않은 요청은 내부 API에서 거부된다.
- AI 서버에는 바깥에서 들어오는 연결을 받는 포트가 없다.
- 저장소와 운영 설정에 서비스 간 인증용 오래 사는 비밀값이 없다. GitHub 비밀값 스캔으로 함께 확인한다.
- 개발용 인증 우회는 운영 설정에서 켤 수 없다.
