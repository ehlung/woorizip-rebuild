# 0011. AI 워커 구성

- 상태: 채택
- 날짜: 2026-11-20
- 관련 문제: P-01, P-03, P-06 ([01-legacy-analysis.md](../01-legacy-analysis.md))

## 맥락

기존 AI 서버는 Flask 개발 서버로 HTTP 요청을 받았다. 무거운 작업은 워커 프로세스에 넘겼지만 요청 스레드가 결과를 기다려 사실상 동기 처리였고, 공용 결과 큐에서 결과가 섞일 수 있었다(P-06). 요청과 응답 형식은 문서와 코드가 달랐고(P-01), Python 버전과 실행 환경이 명시되지 않았다(P-03). 같은 프로젝트 안에서 얼굴 가이드 서버만 FastAPI로 따로 만들어져 있었다.

[리빌드 초기 설계안](README.md#용어)은 AI 서버를 FastAPI로 다시 만들어, 한 코드베이스에 두 역할을 두려 했다. 하나는 SQS에서 분석 작업을 받아 처리하는 워커이고, 다른 하나는 BE만 호출하는 동기 내부 API(촬영 전 얼굴 정렬 가이드, 검색 질의 임베딩)다. 그런데 [ADR 0002](0002-async-analysis.md)에서 AI 워커가 BE에서 작업을 가져가는 구조로 정하면서, AI 쪽은 요청을 받는 서버가 아니라 작업을 꺼내 처리하는 워커가 되었다. [ADR 0005](0005-service-communication.md)는 AI 서버에 바깥에서 들어오는 포트를 두지 않는다고 했다. 그래서 웹 프레임워크가 필요한지부터 다시 판단한다.

워커가 바깥 서비스에 나가서 작업을 받아 오는 구조는 드문 방식이 아니다. 예를 들어 GitHub Actions의 self-hosted runner도 "Self-hosted runners connect to GitHub to receive job assignments"이고, 필요한 네트워크 조건은 "outbound HTTPS connections over port 443"뿐이다(https://docs.github.com/en/actions/reference/runners/self-hosted-runners). 이 문서에는 작업을 받는 방식(polling 여부)까지는 나와 있지 않다.

## 판단 기준

1. 0002의 동작(long polling으로 작업 요청, 결과 보고)을 단순하게 구현한다
2. 바깥에서 들어오는 포트가 없다
3. BE와 주고받는 작업·결과 형식이 명세와 어긋나지 않는다
4. 실행 환경(Python 버전, 의존성)을 누구나 같게 재현할 수 있다
5. 1인 개발로 관리할 수 있다

## 후보

### A. FastAPI 서버 (리빌드 초기 설계안)

- 장점: 타입 기반 검증과 API 문서 자동 생성. 모델을 HTTP API로 바로 응답하는 경우에 많이 쓰인다.
- 단점:
  - 0002 이후로는 AI 쪽이 요청을 받을 일이 없다. 서버를 띄우면 포트가 생긴다(기준 2).
  - FastAPI에는 작업을 가져오는 기능이 없다. FastAPI를 써도 작업 요청 → 처리 → 결과 보고 루프와 그 루프의 종료 처리는 직접 만들어야 한다. 프레임워크와 포트만 늘고 직접 만들 것은 줄지 않는다.

### B. 작업 큐 프레임워크 (Celery 등)

- 장점: 재시도, 동시 실행 수 조절 같은 기능이 갖춰져 있다.
- 단점: 별도 메시지 브로커(Redis, RabbitMQ 등)가 필요하다. 0002에서 작업 상태를 BE의 DB가 관리하기로 했으므로, 재시도와 상태 관리가 두 곳으로 나뉜다(기준 1, 5).

### C. 프레임워크 없는 Python 워커

작업 요청 → 처리 → 결과 보고를 반복하는 Python 프로세스로 만든다. HTTP 클라이언트와 타입 검증 라이브러리만 쓴다.

- 장점: 0002의 동작을 그대로 옮긴 구조다(기준 1). 포트가 없다(기준 2). 의존성이 적다.
- 단점: 상태 확인(health check)과 종료 신호 처리를 직접 만든다. 둘 다 짧은 코드로 된다.
  - 상태 확인: 루프가 마지막으로 작업을 요청한 시각을 파일에 적고, 컨테이너의 상태 확인 명령이 그 시각이 최근인지 본다.
  - 종료 신호: SIGTERM을 받으면 플래그를 세우고, 처리 중인 작업을 마친 뒤 루프를 끝낸다.

## 결정

**C(프레임워크 없는 Python 워커)를 채택한다.** 리빌드 초기 설계안의 FastAPI 선택은 0002로 구조가 바뀌면서 근거가 사라졌다.

- 작업 요청과 결과 보고는 [ADR 0006](0006-repository-and-api-contract.md)에 따라 BE의 OpenAPI 명세에서 생성한 Python 클라이언트로 한다. 작업과 결과의 형식이 명세와 어긋나면 생성 단계에서 드러난다.
- 작업 입력을 검증해, 형식이 맞지 않는 작업은 영구 실패로 보고한다([ADR 0004](0004-failure-and-retry.md)).
- 상태 확인은 포트를 열지 않고 컨테이너의 상태 확인 명령(마지막으로 작업을 요청한 시각 등)으로 한다.
- 종료 신호를 받으면 새 작업을 받지 않고, 처리 중인 작업을 마치거나 실패로 보고한 뒤 종료한다. 끝내지 못한 작업은 lease 만료로 다른 워커가 이어받는다.
- 한 프로세스는 한 번에 작업 하나만 처리한다. 처리량을 늘릴 때는 프로세스 안에서 동시 처리를 늘리지 않고 워커 컨테이너 수를 늘린다. 작업을 가져가는 쪽이 워커이므로 BE 쪽 변경은 없다.
- 초기 설계안의 동기 내부 API는 둘 다 0단계 범위 밖이다. 얼굴 가이드는 1단계, 의미 검색은 2단계다([02-domain-and-problem.md](../02-domain-and-problem.md)). 이 기능을 만들 때 처리 위치(기기 안, BE가 외부 API를 직접 호출, AI 쪽 HTTP 서버)를 따로 정하고, HTTP 서버가 필요하면 그 기능에 한해 FastAPI를 검토한다.
- Python 버전과 의존성은 잠금 파일로 고정하고, 컨테이너 이미지로 실행한다.
- 분석 단계(STT, 요약, 썸네일)는 서로 독립된 모듈로 나눠, 각각 단위 테스트를 둔다. 제공자는 [ADR 0012](0012-ai-provider.md)의 결과에 따라 바꿔 끼울 수 있게 단계마다 인터페이스를 둔다.

## 결과

- 얻는 것: 쓰지 않는 서버 프레임워크와 포트가 없다. 작업 상태 관리가 BE 한 곳에 모인다.
- 잃는 것: 상태 확인과 종료 처리를 직접 만든다. 프로세스 하나의 처리량이 작업 하나로 제한된다.
- 후속 작업: Python 의존성 관리 도구 선택(구현 시)

## 검증

assertion:

- AI 워커 프로세스는 바깥에서 들어오는 연결을 받는 포트를 열지 않는다.
- 형식이 맞지 않는 작업을 받으면 영구 실패로 보고한다.
- 작업을 요청하지 못한 채 정해진 시간이 지나면 컨테이너 상태 확인이 실패한다.
- 워커 컨테이너를 둘로 늘리면 같은 작업을 두 워커가 동시에 처리하지 않는다.
- 종료 신호를 받으면 처리 중인 작업을 마치거나 실패로 보고한 뒤 종료한다.
- 잠금 파일과 컨테이너 이미지만으로 다른 환경에서 같은 의존성으로 실행된다.
- STT, 요약, 썸네일 단계는 각각 단위 테스트가 있다.
