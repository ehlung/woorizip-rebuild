# 0019. refresh token 재사용 판정

- 상태: 채택
- 날짜: 2026-11-27
- 관련 문제: P-14 ([01-legacy-analysis.md](../01-legacy-analysis.md))
- 바꾸는 결정: [ADR 0009](0009-auth-token.md)의 세부 규칙 중 "재사용 감지"

## 맥락

[ADR 0009](0009-auth-token.md)는 refresh token을 쓸 때마다 새것으로 바꾸고(rotation), "이미 무효가 된 refresh token으로 재발급을 시도하면 그 사용자의 refresh token을 모두 폐기한다"고 정했다. 토큰을 훔친 쪽과 원래 사용자가 같은 토큰을 쓰면 서버는 누가 진짜인지 알 수 없으므로, 둘 다 끊는 규칙이다(RFC 9700 4.14.2).

가입·로그인 PR 3을 만들면서 이 규칙이 진짜 사용자를 끊는 경우를 세 가지 찾았다.

1. 로그아웃한 뒤: 앱이 로그아웃 전에 보낸 요청이 늦게 도착하거나 오래된 토큰으로 한 번 더 요청하면, 로그아웃으로 무효가 된 토큰이 온다. 규칙대로면 다른 기기의 로그인까지 모두 끊긴다.
2. 동시 요청: 화면 하나가 API 두 개를 동시에 부르고 둘 다 access token 만료로 같은 refresh token을 보낸다. 첫 요청이 토큰을 바꾸면 두 번째 요청은 바꾼 토큰을 보낸 것이 된다.
3. 응답 유실: 서버가 새 토큰을 발급했는데 연결이 약해 응답이 앱에 닿지 않는다. 앱은 이전 토큰으로 다시 보낸다.

ADR 0009는 앱이 재발급을 한 번만 보내도록 정했다(A-45). 이것은 2번을 막지만 1번과 3번은 막지 못한다. 연세 많은 사용자가 이유 없이 모든 기기에서 로그아웃되면 다시 로그인하지 못하고 서비스를 떠날 수 있다(ADR 0009의 기준 3).

## 판단 기준

1. 토큰을 훔쳐 쓴 경우를 여전히 알아채고 끊는다
2. 진짜 사용자가 네트워크나 앱 동작 때문에 로그아웃되지 않는다
3. 구현과 설명이 단순하다

## 후보

### A. 지금 규칙 그대로 (무효가 된 토큰이 오면 모두 폐기)

- 장점: 가장 엄격하다. 탈취를 놓치는 구간이 없다.
- 단점: 위 1~3번 상황에서 진짜 사용자의 모든 기기가 로그아웃된다(기준 2).

### B. 로그아웃한 토큰은 거부만 하고, 바꾼 토큰은 짧은 유예 시간 동안 받아 준다

- 로그아웃으로 폐기한 토큰이 오면 그 요청만 거부한다. 바꾼(rotation) 토큰이 오면 모두 폐기하되, 바꾼 지 30초 안이면 탈취로 보지 않고 같은 세션의 새 토큰을 한 번 더 준다.
- 장점: 1~3번을 모두 막는다(기준 2). Okta도 같은 이유로 유예 시간을 두며, 기본값은 30초이고 0~60초로 정할 수 있다("the previous token remains valid for this amount of time to allow clients to get the new token.", https://developer.okta.com/docs/guides/refresh-tokens/main/#grace-period-for-token-rotation).
- 단점: 훔친 토큰을 바꾼 지 30초 안에 쓰면 알아채지 못하고, 훔친 쪽도 새 토큰을 받는다(기준 1을 조금 잃음). 로그아웃한 토큰을 훔쳐 써도 모두 끊지는 않는다. 다만 그 토큰으로는 새 토큰을 받지 못한다.

### C. 앱의 재발급 한 번만 보내기(A-45)에만 맡긴다

- 장점: 서버 규칙은 A 그대로라 단순하다.
- 단점: 2번만 막고 1번과 3번은 막지 못한다(기준 2).

## 결정

**B를 채택한다.** 사용자가 2026-11-26에 정했다.

- 로그아웃한 토큰을 거부만 하는 것은 탐지를 잃지 않는다. 로그아웃으로 폐기한 토큰은 이미 새 토큰을 받을 수 없어서, 훔친 쪽이 얻는 것이 없다.
- 유예 시간은 Okta 기본값과 같은 30초로 한다. 30초 안에 탈취를 놓치는 위험보다, 진짜 사용자가 모든 기기에서 로그아웃되는 일이 이 서비스에는 더 크다고 판단했다. 30초가 지나 바꾼 토큰이 오면 지금처럼 모두 폐기한다.
- 앱의 재발급 한 번만 보내기(A-45)는 그대로 둔다. 서버 유예 시간은 앱이 놓친 경우를 받는 안전장치다.

### 세부 규칙

- 바꾼 시각은 처음 바꾼 때로 둔다. 유예 시간 안에 다시 와도 바꾼 시각을 갱신하지 않아, 유예 시간이 계속 늘어나지 않는다.
- 유예 시간 안에 다시 온 토큰에는 같은 세션의 새 토큰을 준다. 처음 발급한 새 토큰도 그대로 쓸 수 있다.
- 만료된 토큰은 유예 시간 안이어도 거부한다.

## 결과

- 얻는 것: 로그아웃 직후의 늦은 요청, 동시 요청, 응답 유실로 사용자가 로그아웃되지 않는다.
- 잃는 것: 바꾼 지 30초 안에 훔친 토큰을 쓰면 알아채지 못한다.
- 후속 작업: 운영 로그에서 유예 시간 안 재요청과 재사용 감지가 얼마나 일어나는지 보고 30초를 다시 판단한다. 시점: 테스트 배포 1차 피드백 뒤.

## 검증

assertion:

- 바꾼 지 30초가 지난 refresh token으로 재발급을 시도하면 그 사용자의 모든 refresh token이 폐기된다(ADR 0009의 재사용 감지를 바꾼 것).
- 같은 refresh token으로 동시에, 또는 바꾼 지 30초 안에 다시 재발급해도 성공하고 토큰이 폐기되지 않는다.
- 로그아웃으로 폐기한 refresh token으로 재발급하면 거부되고, 다른 기기의 로그인은 유지된다.
