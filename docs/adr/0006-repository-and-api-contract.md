# 0006. 저장소 구성과 API 명세 공유

- 상태: 채택
- 날짜: 2026-11-20
- 관련 문제: P-01, P-02, P-03 ([01-legacy-analysis.md](../01-legacy-analysis.md))

## 맥락

기존 프로젝트는 FE, BE, AI를 세 저장소로 나눠 각자 한 명이 개발했다. 공유하는 API 명세가 없어 세 서비스의 약속이 어긋났다. FE는 응답 필드 이름을 추측했고, BE는 AI 서버에 없는 엔드포인트를 호출했으며, AI README와 실제 응답 형식도 달랐다(P-01). 서비스 주소는 코드 여러 곳에 하드코딩되어 있었고(P-02), 세 서비스를 한 번에 띄우는 방법이 없어 통합 문제를 배포 직전에야 발견했다(P-03).

리빌드는 1인 개발이다. 저장소를 나눴던 이유(세 사람이 따로 일함)가 더 이상 없다. 클라이언트는 앱(0단계)과 웹(2단계) 두 개가 되고, 둘은 디자인 토큰과 API 클라이언트를 공유한다.

## 판단 기준

1. 서버의 요청·응답 형식이 바뀌면 클라이언트에서 바로 드러난다
2. BE와 AI 워커 사이의 내부 API도 같은 방식으로 관리한다
3. 전체 서비스를 한 번에 실행하고 검증할 수 있다
4. 1인 개발로 관리할 수 있다
5. 저장소 구성과 배포 단위를 분리해서 생각할 수 있다

## 후보

### 저장소 구성

#### A. 서비스별 저장소 유지

- 장점: 서비스마다 이력과 권한이 깔끔하게 나뉜다.
- 단점: 명세 공유, 생성 코드 배포, 버전 맞추기를 저장소 사이에서 해야 한다(기준 1, 4). 기존 프로젝트의 문제가 이 구조에서 생겼다.

#### B. 모노레포

`apps/mobile`, `apps/api`, `apps/ai`, `packages/*`를 한 저장소에 둔다.

- 장점: 서버 변경과 생성된 클라이언트 변경이 한 커밋에 함께 들어간다(기준 1). 한 명령으로 전체를 실행하는 설정을 한곳에 둘 수 있다(기준 3).
- 단점: 언어가 셋(TypeScript, Java, Python)이라 빌드 도구가 섞인다. CI에서 바뀐 부분만 빌드하도록 설정해야 한다.

### 명세를 만드는 방식

#### 코드 우선 (code-first)

Spring 코드에서 OpenAPI 명세를 생성하고(springdoc-openapi), 명세에서 클라이언트를 생성한다.

- 장점: 서버 코드가 곧 명세라 둘이 어긋나지 않는다. 1인 개발에서 관리할 파일이 적다.
- 단점: 명세가 서버 구현에 끌려가기 쉽다.

#### 명세 우선 (spec-first)

OpenAPI 명세를 먼저 쓰고, 서버와 클라이언트 코드를 명세에서 생성한다.

- 장점: 구현 전에 API를 설계하고 검토할 수 있다. 여러 팀이 동시에 개발할 때 유리하다.
- 단점: 명세 파일과 생성된 서버 코드를 함께 관리해야 한다. 1인 개발에서는 얻는 것보다 관리 부담이 크다.

## 결정

**B(모노레포)와 코드 우선 방식을 채택한다.**

- 공개 API와 내부 API(AI 워커용) 모두 Spring 코드에서 OpenAPI 명세를 생성한다.
- 명세에서 앱용 TypeScript 클라이언트(`packages/api-client`)와 AI 워커용 Python 클라이언트를 생성한다.
- CI에서 명세를 다시 생성해, 커밋된 생성 코드와 다르면 실패시킨다. 서버를 바꾸고 클라이언트를 다시 생성하지 않으면 병합할 수 없다.
- 서비스 주소는 코드에 쓰지 않고 환경 설정 한 곳에서 읽는다([ADR 0014](0014-secrets-and-config.md)).
- 전체 서비스를 한 명령으로 실행하는 방법은 [ADR 0016](README.md)에서 정한다.

저장소는 하나지만 배포 단위는 나뉜다. 앱, API 서버, AI 워커는 각자 따로 빌드하고 배포한다. 배포 형태는 ADR 0017에서 정한다.

A는 기존 문제의 원인인 "저장소 사이의 약속 맞추기"를 그대로 남긴다. 명세 우선 방식은 여러 팀이 병렬로 개발할 때의 장점이 1인 개발에서는 크지 않다.

## 결과

- 얻는 것: 서버와 클라이언트의 약속이 어긋나면 빌드나 CI에서 바로 드러난다. 한 저장소에서 전체 흐름을 실행하고 검증한다.
- 잃는 것: 언어가 셋인 저장소를 관리해야 한다. CI 설정이 복잡해진다.
- 후속 작업: 클라이언트 생성 도구 선택(구현 시), CI에서 바뀐 앱만 빌드하는 설정
  - 클라이언트 생성 도구는 Orval 8.x로 정했다(2026-11-25). 처음 검토한 openapi-typescript는 2026-09-19에 유지보수가 끝났고(https://github.com/openapi-ts/openapi-typescript/issues/2874) TypeScript 6을 지원하지 않았다. 명세는 API 서버 테스트가 `packages/api-client/openapi.json`에 쓰고, CI는 그 명세로 클라이언트를 다시 생성해 커밋된 것과 다르면 실패한다.

## 검증

assertion:

- 서버의 응답 필드를 바꾸고 클라이언트를 다시 생성하면, 그 필드를 쓰는 앱 코드는 타입 검사에서 실패한다.
- 커밋된 생성 클라이언트가 현재 서버 명세와 다르면 CI가 실패한다.
- 코드 안에 서비스 주소(호스트, IP)가 하드코딩되어 있지 않다.
