# 0009. 인증 토큰의 발급, 저장, 갱신

- 상태: 채택
- 날짜: 2026-11-20
- 관련 문제: P-12, P-14, P-15 ([01-legacy-analysis.md](../01-legacy-analysis.md)), 01의 부록 A(이메일 변경 시 토큰 불일치)

## 맥락

기존 프로젝트의 인증은 다음 문제가 있었다.

- JWT 서명 키가 공개 저장소의 소스 코드에 있어, 이메일만 알면 누구나 토큰을 만들 수 있었다 (P-12)
- 토큰은 1시간짜리 JWT 하나였고 갱신 토큰이 없었다. 앱은 `localStorage`에 저장했고, 로그인 확인은 시작할 때 한 번뿐이었으며, 401 처리가 화면마다 달랐다 (P-14)
- 비밀번호 재설정 코드는 메모리에 저장되고 시도 횟수 제한이 없었다. 가입 중 비밀번호를 화면 이동 데이터(router state)로 넘겼다 (P-15)
- 토큰이 사용자를 이메일로 식별해, 이메일을 바꾸면 이후 요청이 실패했다 (01의 부록 A)

P-12의 원인은 JWT라는 방식이 아니라 서명 키를 코드에 직접 적은 관리 방식이다. 비밀값 관리는 [ADR 0014](0014-secrets-and-config.md)에서 따로 정한다.

[리빌드 초기 설계안](README.md#용어)은 짧은 access token(JWT)과 DB에 저장하는 refresh token, refresh token rotation을 쓰기로 했다. 이 선택이 위 문제와 아래 조건에 맞는지 다시 검토한다.

사용자 중에는 연세가 많은 분이 있어, 자주 다시 로그인해야 하면 서비스를 포기할 수 있다. 계정을 지우거나(회원 탈퇴), 비밀번호를 재설정하거나, 기기를 잃어버렸을 때는 기존 로그인을 끊을 수 있어야 한다.

## 판단 기준

1. 서명 키 같은 비밀값이 새도 피해를 줄이고 복구할 절차가 있다
2. 로그아웃, 회원 탈퇴, 비밀번호 재설정 때 기존 로그인을 끊을 수 있고, 끊기기까지 남는 시간이 짧다
3. 연세가 많은 사용자가 자주 다시 로그인하지 않는다
4. 널리 쓰이는 방식이라 라이브러리와 문서의 도움을 받을 수 있다
5. 2단계의 웹 클라이언트와 1단계의 소셜 로그인에도 같은 체계를 쓸 수 있다

## 후보

### A. JWT 하나 (기존)

- 장점: 단순하다.
- 단점: 발급한 토큰을 만료 전에 끊을 수 없다(기준 2). 유효시간을 길게 하면 위험이 커지고, 짧게 하면 자주 다시 로그인해야 한다(기준 3). 서명 키를 바꾸면 모든 사용자가 다시 로그인해야 한다(기준 1).

### B. JWT access token + refresh token rotation (리빌드 초기 설계안)

access token은 짧게(15분) JWT로 발급하고, refresh token은 DB에 저장해 쓸 때마다 새것으로 바꾼다. 이미 쓴 refresh token으로 재발급을 시도하면 탈취로 보고 그 사용자의 refresh token을 모두 폐기한다.

- 장점:
  - 널리 쓰이는 방식이다(기준 4). access token은 DB 조회 없이 검증할 수 있어 서버가 늘어도 세션 저장소가 필요 없다.
  - 로그아웃, 탈퇴, 재설정 때 refresh token을 폐기하면 access token이 만료되는 15분 안에 끊긴다(기준 2).
  - refresh token은 서명 키와 관계없는 DB 값이다. 서명 키를 바꾸면 기존 access token은 거부되지만, 앱이 refresh token으로 한 번 재발급받으면 되므로 사용자가 다시 로그인하지 않는다(기준 1, 3).
- 단점: 서명 키를 관리해야 한다. 끊긴 뒤에도 access token이 최대 15분 남는다. 서버의 rotation과 재사용 감지, 앱의 동시 401 처리(재발급을 한 번만 요청)까지 구현할 것이 C보다 많다.

### C. 불투명 세션 토큰 (opaque token)

서버가 의미 없는 긴 난수를 토큰으로 발급하고, DB에는 그 해시만 저장한다. 요청마다 해시로 세션을 찾아 사용자를 확인한다.

- 장점: 서명 키가 없다. DB에서 세션을 지우면 그 즉시 끊긴다. 토큰 하나라 앱의 갱신 처리가 단순하다.
- 단점: 요청마다 세션 조회가 한 번 늘어나고, 서버가 늘면 세션 캐시가 필요하다. 인증 처리를 라이브러리보다 직접 작성하는 부분이 많다(기준 4).

## 결정

**B(JWT access token + refresh token rotation)를 채택한다.** 리빌드 초기 설계안의 선택을 유지한다.

- C의 장점인 "서명 키가 없다"는 기존 문제(P-12)를 방식의 문제로 본 것이다. 원인은 키를 코드에 둔 관리 방식이고, 이는 0014로 막는다. 키가 새더라도 B는 키를 바꾸고 refresh token으로 재발급받는 절차로 다시 로그인 없이 복구한다.
- C의 다른 장점인 "즉시 끊김"과 B의 차이는 최대 15분이다. 이 15분은 받아들이는 위험으로 둔다. 가족 데이터는 [ADR 0008](0008-family-authorization.md)에 따라 요청마다 활성 구성원인지 DB로 확인하므로, 탈퇴하거나 가족을 나간 사용자는 access token이 남아 있어도 가족 데이터에 바로 접근하지 못한다. 15분 동안 남는 것은 가족과 무관한 API(내 정보 조회 등)다.
- 구현할 양은 B가 C보다 많다. 대신 널리 쓰이는 방식이라 라이브러리와 문서를 쓸 수 있고, 2단계 웹과 1단계 소셜 로그인도 같은 체계로 처리한다. Spring Security의 JWT 검증 지원 범위는 구현할 때 공식 문서로 확인한다.
- A는 기준 1~3을 만족하지 못한다.

### 세부 규칙

- **access token**: JWT, 유효시간 15분. 토큰은 사용자 ID에 연결하며 이메일에 연결하지 않는다.
- **서명 키**: 0014에 따라 Parameter Store에 둔다. 키를 바꿀 수 있도록 토큰 헤더에 키 ID(`kid`)를 넣는다. 키가 새면 새 키를 발급하고 이전 키를 폐기한다. 이전 키로 서명된 access token은 거부되고, 앱은 refresh token으로 재발급받는다.
- **refresh token**: 보안 난수로 만든 256비트 값이고, DB에는 해시만 저장한다. 재발급할 때마다 새 refresh token을 발급하고 이전 것을 무효로 한다.
- **재사용 감지**: 이미 무효가 된 refresh token으로 재발급을 시도하면 그 사용자의 refresh token을 모두 폐기한다.
- **수명**: refresh token은 마지막 사용 후 30일 동안 쓰지 않으면 만료된다. 쓰는 동안은 연장되며, 처음 로그인한 뒤 최대 1년이 지나면 다시 로그인한다.
- **폐기**: 로그아웃하면 그 기기의 refresh token을, 회원 탈퇴와 비밀번호 재설정 때는 그 사용자의 모든 refresh token을 폐기한다. 이미 발급된 access token은 만료될 때까지(최대 15분) 남는다.
- **앱 저장**: refresh token은 기기의 보안 저장소(Expo SecureStore)에, access token은 메모리에 둔다. 공통 HTTP 계층이 401을 받으면 재발급을 한 번만 요청하고, 그동안 들어온 요청은 재발급 결과를 기다린다. 재발급이 실패하면 로그인 화면으로 보낸다.
- **비밀번호 저장**: BCrypt 해시로 저장한다(기존 방식 유지).
- **로그인 실패**: 이메일이 없을 때와 비밀번호가 틀렸을 때 같은 메시지를 돌려준다. 같은 계정에 연속으로 실패하면 시도 간격을 늘린다.
- **비밀번호 재설정**: 6자리 코드를 보안 난수로 만들고 DB에 해시로 저장한다. 10분 뒤 만료되고, 5회 틀리면 무효가 된다. 같은 이메일로 코드를 요청하는 횟수에 제한을 둔다. 재설정이 끝나면 모든 refresh token을 폐기한다.
- **가입 정보**: 앱은 가입 중 입력한 비밀번호를 화면 이동 데이터에 담지 않고, 가입 화면 흐름 안의 메모리 상태로만 다룬다.
- **소셜 로그인(1단계)**: 카카오, 구글, 애플이 발급한 토큰을 서버가 검증한 뒤 같은 access token과 refresh token을 발급한다.

## 결과

- 얻는 것: 널리 쓰이는 방식으로 인증을 만든다. 로그아웃, 탈퇴, 비밀번호 재설정 때 15분 안에 끊기고, 가족 데이터는 바로 막힌다. 서명 키가 새도 다시 로그인 없이 복구한다.
- 잃는 것: 서명 키를 관리해야 한다. 끊긴 뒤에도 access token이 최대 15분 남는다. rotation, 재사용 감지, 앱의 동시 401 처리를 구현한다.
- 후속 작업: 서명 알고리즘과 Spring Security 설정은 구현할 때 정한다.
  - 서명은 HS256으로 정했다(2026-11-25). 토큰을 발급하는 곳과 검증하는 곳이 모두 API 서버라 공개키 방식이 필요 없다. 키는 32바이트(256비트) 이상이어야 한다(RFC 7518 3.2). 검증할 때는 헤더의 `kid`로 설정의 키 목록에서 키를 고른다.
  - "이미 무효가 된 refresh token"을 두 가지로 나눠 처리한다(2026-11-26). 쓸 때마다 바꾼(rotation) 토큰이 다시 오면 탈취로 보고 그 사용자의 refresh token을 모두 폐기한다. 로그아웃으로 폐기한 토큰이 오면 그 요청만 거부한다. 로그아웃한 뒤 앱이 오래된 토큰으로 한 번 더 요청하는 경우에 다른 기기의 로그인까지 끊지 않으려는 것이다. A-40은 바꾼 토큰으로 확인한다.
  - 바꾼(rotation) refresh token이 다시 와도 바꾼 지 30초 안이면 탈취로 보지 않고 같은 세션의 새 토큰을 준다(2026-11-26). 같은 토큰으로 동시에 보낸 요청이나, 새 토큰을 담은 응답이 앱에 닿지 않아 다시 보낸 요청에 사용자가 모든 기기에서 로그아웃되지 않게 한다. Okta의 유예 시간 기본값(30초)과 같다. 훔친 토큰을 30초 안에 쓰면 탐지하지 못하는 위험은 받아들인다.
  - 로그인 실패 제한의 숫자를 정했다(2026-11-26). 같은 이메일로 5번 연속 실패하면 30초 잠그고 실패마다 2배로 늘린다(최대 15분). 연속 100번 실패하면 비밀번호를 재설정해야 한다(NIST SP 800-63B-4의 연속 실패 상한). 근거는 [plans/auth.md](../plans/auth.md)의 정한 것에 있다.
  - Spring Security는 모든 요청에 access token을 요구하고, 로그인 없이 쓰는 주소(가입, 로그인, 토큰 재발급, 비밀번호 재설정)는 그 기능을 만들 때 하나씩 연다.

## 검증

assertion:

- 저장소 전체 이력에 서명 키가 없다(0014의 gitleaks 검사와 같은 확인).
- 만료된 access token으로 요청하면 401을 받고, refresh token으로 재발급받으면 다시 요청할 수 있다.
- 로그아웃한 기기의 refresh token으로 재발급을 요청하면 거부된다.
- 비밀번호를 재설정하면 그 사용자의 다른 기기 refresh token도 거부된다.
- 이미 쓴 refresh token으로 재발급을 시도하면 그 사용자의 모든 refresh token이 폐기된다.
- 30일 동안 쓰지 않은 refresh token은 거부된다.
- DB에는 refresh token 원문이 아니라 해시만 저장된다.
- 탈퇴한 사용자의 만료 전 access token으로 가족 API를 요청하면 거부된다.
- 서명 키를 바꾼 뒤 이전 키로 서명된 access token은 거부되고, refresh token으로 재발급받으면 다시 로그인하지 않고 쓸 수 있다.
- 앱이 동시에 여러 401을 받아도 재발급 요청은 한 번만 보낸다.
- 재설정 코드는 10분 뒤, 또는 5회 틀린 뒤에는 맞게 입력해도 거부된다.
- 로그인 실패 응답으로 이메일 가입 여부를 알 수 없다.
- 사용자의 이메일이 바뀌어도 기존 로그인은 계속 유효하다.
