# 0002. 업로드 후 AI 분석을 요청과 분리하는 방식

- 상태: 채택
- 날짜: 2026-11-20
- 관련 문제: P-05, P-06, P-08, P-10 ([01-legacy-analysis.md](../01-legacy-analysis.md))

## 맥락

기존에는 사용자가 영상을 올리면 S3 저장, 썸네일 AI 호출, 요약 AI 호출, DB 저장이 한 번의 요청 안에서 모두 끝나야 응답했다.

```
앱 ──요청──▶ BE: S3 저장 → AI 썸네일 → AI 요약 → DB 저장 ──응답──▶ 앱
             (수십 초~수 분 동안 사용자는 로딩 화면에서 대기)
```

이 구조에서 다음 문제가 생겼다.

- 요청 스레드와 DB 커넥션이 AI 분석 내내 묶이고, 타임아웃이 없다 (P-05)
- AI 서버 내부의 결과 큐가 요청 간에 섞일 수 있다 (P-06)
- 실패하면 전체가 롤백되고, 다시 시도할 방법이 없다 (P-08)
- 앱은 기다리는 동안 취소도 복구도 할 수 없다 (P-10)

기존에 후속 작업(반려동물 숏츠)에 쓴 `@Async`도 서버가 재시작되면 진행 중인 작업이 사라지고 다시 시도할 경로가 없었다(01의 부록 A).

모바일에서는 요청이 길어질수록 더 불리하다. 사용자가 화면을 끄거나 다른 앱으로 이동하면 요청이 끊길 수 있다. 영상은 최대 3분이고, 분석에는 수십 초에서 몇 분이 걸릴 것으로 예상한다(실측 전).

## 판단 기준

1. 서버 재시작, 배포, 워커 장애가 있어도 분석 작업이 사라지지 않는다
2. 시도 횟수와 실패 상태를 기록해 재시도와 실패 처리를 할 수 있다
3. 업로드 응답 시간이 분석 시간과 무관하다
4. 1인 개발과 운영으로 감당할 수 있는 인프라다
5. 규모가 커졌을 때 다른 방식으로 옮겨 갈 수 있다
6. AI 서버가 바깥에 노출되는 범위를 줄인다

## 후보

### 분석을 요청과 분리하는 방식

#### A. 동기 처리 유지, 타임아웃만 추가

- 장점: 바꿀 것이 거의 없다.
- 단점: 업로드 응답 시간이 곧 분석 시간이라는 근본 문제가 남는다(기준 3). 실패하면 여전히 처음부터 다시 올려야 한다.

#### B. Spring `@Async`

업로드 요청은 바로 응답하고, BE 메모리 안의 스레드에서 분석을 실행한다.

- 장점: 가장 간단하다. 새 인프라가 없다.
- 단점: 작업이 메모리에만 있어 서버가 재시작되거나 배포되면 사라진다(기준 1). 시도 횟수와 상태가 남지 않아 재시도를 관리하기 어렵다(기준 2). 기존 숏츠에서 같은 문제가 있었다.

#### C. DB 작업 테이블

답변을 저장하는 트랜잭션 안에서 분석 작업 행을 함께 저장한다. 워커가 대기 중인 작업을 꺼내 처리한다.

- 장점: 답변과 작업이 함께 저장되거나 함께 실패하므로 작업이 사라지지 않는다(기준 1). 상태와 시도 횟수가 DB에 남는다(기준 2). 새 인프라가 필요 없다(기준 4).
- 단점: 워커가 새 작업을 알아채는 만큼 시작이 늦을 수 있다. 여러 워커가 같은 작업을 꺼내지 않도록 잠금이 필요하다. DB가 큐 역할을 함께 하므로, 규모가 커지면 부담이 될 수 있다.

#### D. 메시지 큐 (SQS 등)

작업을 큐에 넣고 워커가 받아 처리한다.

- 장점: 규모가 커져도 버티고, 서비스 간 결합이 가장 느슨하다.
- 단점: 운영할 인프라가 늘어난다(기준 4). DB 저장은 됐는데 큐 발행이 실패하는 경우를 막으려면 Outbox 같은 장치가 추가로 필요하다.

### C를 고를 때 워커의 위치

#### C1. BE 안의 워커가 AI 서버를 호출

- 장점: AI 서버는 요청을 받아 처리하기만 하면 된다.
- 단점: BE와 AI 서버 사이에 몇 분짜리 요청이 생겨 타임아웃을 관리해야 한다. AI 서버가 BE의 요청을 받기 위해 포트를 열어 두어야 한다(기준 6).

#### C2. AI 서버의 워커가 BE에서 작업을 가져감

AI 워커가 BE 내부 API에 다음 작업을 요청해 받아 가고, 끝나면 결과를 보고한다.

- 장점: 오래 걸리는 요청이 없다. AI 서버는 바깥에서 들어오는 연결을 받을 필요가 없어 열린 포트가 없다(기준 6). 워커를 늘려도 BE를 바꿀 필요가 없다. 큐 방식(D)과 모양이 같아 나중에 옮기기 쉽다(기준 5).
- 단점: 워커가 작업 도중 멈추는 경우를 처리해야 한다.

### 워커가 새 작업을 알아채는 방법

| 방법 | 특징 |
| --- | --- |
| polling | 몇 초마다 새 작업이 있는지 묻는다. 가장 단순하지만 작업이 없어도 계속 요청한다 |
| long polling | 묻고 나서 새 작업이 생길 때까지 최대 수십 초 응답을 기다린다. 작업이 생기면 바로 받는다 |
| LISTEN/NOTIFY | 작업이 추가되면 PostgreSQL이 알려 준다. 연결이 끊긴 동안의 알림은 놓치므로 polling을 함께 둬야 한다 |

### 앱이 분석 완료를 알아채는 방법

| 방법 | 특징 |
| --- | --- |
| polling | 분석 중인 답변이 화면에 있을 때만 몇 초마다 다시 조회한다. 앱을 보고 있을 때만 동작한다 |
| SSE | 서버가 열린 연결로 변화를 보내 준다. 앱이 백그라운드로 가면 연결이 끊기고, 서버가 여러 대면 추가 장치가 필요하다 |
| WebSocket | 양방향 연결이다. 우리 용도(완료 알림 한 번)에는 과하다 |
| 푸시 알림 | 앱을 닫아 둬도 받는다 |

## 결정

**C(DB 작업 테이블) + C2(AI 워커가 작업을 가져감)를 채택한다.** 워커는 long polling으로 작업을 요청하고, 앱은 분석 중일 때 polling하고 앱 밖에 있을 때는 푸시 알림으로 완료를 받는다.

- A는 기준 3을, B는 기준 1과 2를 만족하지 못한다. B는 기존 숏츠에서 같은 문제가 실제로 있었다.
- D는 기준 1~3을 만족하지만, 지금 규모에서는 운영 부담에 비해 얻는 것이 적다. 작업 테이블로 운영해 보고 한계가 확인되면 옮긴다. C2는 워커가 "작업을 가져가 처리하고 결과를 보고하는" 모양이라, 큐로 옮겨도 워커의 구조는 거의 그대로다.
- C1은 AI 서버가 포트를 열어 두어야 하고, BE와 AI 사이의 긴 요청을 관리해야 한다. C2는 AI 서버에 들어오는 연결이 없어 P-21 같은 노출이 생기지 않는다.
- 워커는 long polling을 쓴다. 작업이 생기면 바로 시작하면서, 작업이 없을 때의 반복 요청을 줄인다. LISTEN/NOTIFY는 polling을 함께 둬야 해서 지금은 쓰지 않는다.
- 앱은 사용자가 업로드 후 대부분 앱을 떠난다는 점을 고려했다. 앱 밖에 있는 동안 끝난 분석은 푸시 알림이, 홈 화면을 보는 동안 끝난 분석은 짧은 polling이 맡는다. 이에 따라 분석 완료 푸시 알림을 1단계에서 0단계로 옮긴다. SSE는 개선 후보로 둔다.

### 동작 방식

```
1. 앱이 영상을 올림
2. BE: 한 트랜잭션으로 답변(분석 중)과 분석 작업(대기)을 저장 → 즉시 응답
3. AI 워커: BE에 다음 작업을 요청 (long polling)
4. BE: 대기 중인 작업 하나를 잠그고(SKIP LOCKED) "처리 중"으로 바꾼 뒤,
       lease 만료 시각과 시도 횟수를 기록해 워커에 넘김
5. AI 워커: 분석 후 결과를 BE에 보고
6. BE: 답변에 결과를 반영하고 "완료"로 바꿈 → 작성자에게 푸시 알림
```

- **lease**: 작업을 넘길 때 "이 시각까지 결과를 보고해야 한다"는 만료 시각을 함께 기록한다. 워커가 도중에 멈춰 만료 시각까지 보고가 없으면, 작업을 다시 대기 상태로 돌려 다른 워커가 가져가게 한다.
- **잠금**: `SELECT ... FOR UPDATE SKIP LOCKED`로 다른 워커가 잡은 행을 건너뛰고 가져온다. PostgreSQL과 MySQL 8 모두 지원한다.
- 표와 API의 구체적인 모양은 [03-architecture.md](../03-architecture.md)에서 정한다.

## 결과

- 얻는 것:
  - 업로드가 분석과 무관하게 바로 끝나고, 사용자는 홈으로 돌아가 "AI 분석 중" 상태를 본다.
  - 서버 재시작, 배포, 워커 장애에도 작업이 남고 이어서 처리된다.
  - AI 서버에 들어오는 연결이 없다.
- 잃는 것:
  - 워커가 멈추면 lease 시간만큼 처리가 늦어진다.
  - BE에 내부 API(작업 요청, 결과 보고)와 작업 테이블이 추가된다.
  - DB가 큐 역할을 함께 한다. 지금 규모에서는 문제가 없을 것으로 보지만 실측 전이다.
- 후속 작업:
  - 0003: AI 워커가 영상을 어떤 경로로 받는지
  - 0004: 실패 상태, 재시도 횟수, lease 만료 후 늦게 도착한 결과 처리
  - 0005: BE 내부 API의 인증과 AI 서버 보호
  - STATUS: 분석 완료 푸시 알림을 0단계로 이동

## 검증

assertion:

- AI 워커를 멈춘 상태에서도 업로드 요청은 성공하고, 답변은 "분석 중"으로 저장된다.
- BE를 재시작해도 대기 중이던 작업이 사라지지 않고, 재시작 후 처리된다.
- 워커를 처리 도중 종료하면, lease 시간이 지난 뒤 다른 워커가 같은 작업을 다시 처리한다.
- 워커 두 개가 동시에 작업을 요청해도 같은 작업을 받지 않는다.
- 분석이 끝나면 화면을 보고 있는 앱은 polling으로, 앱 밖에 있는 작성자는 푸시 알림으로 완료를 받는다.

지표:

- 업로드 응답 시간 (분석 시간과 무관해야 한다)
- 업로드 완료부터 분석 시작까지의 지연
- 분석 소요 시간 (영상 길이별)
