# 0010. DB 선택과 스키마 관리

- 상태: 채택
- 날짜: 2026-11-20
- 관련 문제: P-04, P-17 ([01-legacy-analysis.md](../01-legacy-analysis.md))

## 맥락

기존 BE는 MySQL을 썼고, JPA와 MyBatis를 함께 썼다. 저장소에 스키마 파일이나 마이그레이션이 없어 새 환경에서 DB를 재현할 수 없었고, 운영은 엔티티를 보고 테이블을 자동으로 바꾸는 `ddl-auto=update`로 실행했다(P-04). MyBatis로만 쓰는 테이블은 엔티티도 없었다. 목록을 만들 때 항목마다 작성자를 따로 조회하는 N+1 쿼리가 있었다(P-17). 로컬과 운영의 MyBatis 설정이 달라 운영에서만 생기는 버그도 있었다(01의 4장).

리빌드에서 DB를 정할 때 고려할 사실은 다음과 같다.

- 기존 운영 데이터가 남아 있지 않다. DB를 바꿔도 옮길 데이터가 없다.
- 2단계에 의미 검색(벡터 검색)이 있다.
- 가족 소속 규칙이 단계에 따라 바뀐다. 0단계에서는 한 사용자가 활성 상태의 가족 하나에만 속한다. 3단계에서는 여러 가족에 속할 수 있게 열고([STATUS.md](../STATUS.md)의 3단계, [ADR 0008](0008-family-authorization.md)의 기준 4), 그때 규칙은 "같은 가족에는 활성 소속이 하나"가 된다. 두 단계 모두 가족을 나간 기록은 남기면서 활성 소속만 제한해야 하고, 3단계에서는 나갔던 가족에 다시 들어올 수도 있어야 한다.
- 개발자는 PostgreSQL을 써 봤다.

## 판단 기준

1. 스키마를 코드로 관리하고, 빈 DB에서 같은 스키마를 재현할 수 있다
2. 서비스 규칙(활성 소속 제한 등)을 DB 제약으로 표현할 수 있고, 규칙이 바뀌어도 제약을 바꾸기 쉽다
3. 스키마 변경이 중간에 실패해도 DB가 어중간한 상태로 남지 않는다
4. 2단계 의미 검색을 DB를 하나 더 두지 않고 처리할 수 있다
5. 조회 방식이 하나로 통일되고, N+1 같은 문제를 테스트로 잡을 수 있다

## 후보

### DB

#### A. MySQL (기존)

- 장점: 기존 프로젝트와 같다. 국내에서 많이 쓴다.
- 단점:
  - 조건이 붙은 인덱스(partial index)가 없다. MySQL 8.4의 `CREATE INDEX` 문법에는 `WHERE` 절이 없다(https://dev.mysql.com/doc/refman/8.4/en/create-index.html). 활성 소속 제한을 제약으로 걸려면 생성 컬럼 같은 우회가 필요하고, 3단계에서 규칙이 바뀔 때도 우회를 다시 만들어야 한다(기준 2).
  - 테이블 구조 변경(DDL)은 트랜잭션 안에서 실행되지 않고 암묵적으로 커밋된다(https://dev.mysql.com/doc/refman/8.4/en/implicit-commit.html). Flyway 문서도 이런 DB에서는 실패한 마이그레이션을 깨끗하게 되돌리지 못하고 수동 정리가 필요할 수 있다고 설명한다(https://documentation.red-gate.com/fd/migration-transaction-handling-273973399.html). 마이그레이션이 중간에 실패하면 일부만 적용된 채 남을 수 있다(기준 3).
  - 벡터 검색을 하려면 별도 벡터 DB나 다른 방법이 필요하다(기준 4).

#### B. PostgreSQL

- 장점:
  - 조건이 붙은 인덱스를 지원한다(https://www.postgresql.org/docs/current/indexes-partial.html). 조건이 붙은 유니크 인덱스로 두 단계의 규칙을 모두 DB가 보장한다(기준 2).
    - 0단계: `UNIQUE (user_id) WHERE status = 'ACTIVE'`. 활성 가족은 하나다.
    - 3단계: `UNIQUE (family_id, user_id) WHERE status = 'ACTIVE'`. 같은 가족에는 활성 소속이 하나다. 나간 기록이 남아 있어도 같은 가족에 다시 들어올 수 있어야 하므로, 이때도 조건 없는 유니크 제약으로는 안 되고 조건이 붙은 인덱스가 필요하다.
    - 규칙을 바꿀 때는 인덱스를 바꾸는 마이그레이션 하나로 처리한다.
  - 테이블 구조 변경도 트랜잭션 안에서 실행되어, 마이그레이션이 실패하면 전체가 되돌아간다(기준 3).
  - pgvector 확장으로 같은 DB에서 벡터 검색을 하고, 가족 조건과 함께 거를 수 있다(기준 4).
- 단점: 기존 프로젝트와 DB가 달라진다. 다만 옮길 데이터가 없어 전환 비용은 거의 없다.

### 스키마 관리

| 후보 | 특징 |
| --- | --- |
| JPA 자동 생성 (`ddl-auto=update`, 기존) | 엔티티를 바꾸면 테이블이 자동으로 바뀐다. 변경 이력이 남지 않고, 의도하지 않은 변경이 운영에 바로 반영된다 |
| Flyway | 버전 번호가 붙은 SQL 파일로 변경 이력을 관리한다. Spring Boot가 시작할 때 적용한다 |
| Liquibase | XML·YAML 등으로 변경을 기술한다. DB 종류를 바꿔도 같은 기술을 쓸 수 있다 |

### 조회 방식

| 후보 | 특징 |
| --- | --- |
| JPA + MyBatis 혼용 (기존) | 같은 테이블을 두 방식으로 다뤄 설정 차이로 인한 버그가 생겼다 |
| JPA만 사용 | 조회는 JPQL과 fetch join, DTO projection으로 처리한다 |
| JPA + QueryDSL | 조건이 많은 조회를 타입 안전하게 작성한다. 원래 저장소(querydsl/querydsl)는 2024-01의 5.1.0 이후 릴리스가 없고, 포크(OpenFeign/querydsl)가 2026-09의 7.7까지 릴리스를 이어 가고 있다. 포크의 README는 원래 저장소를 "at best stale, at worse dead"라고 설명한다 |

## 결정

**PostgreSQL을 쓰고, 스키마는 Flyway로 관리하며, 조회는 JPA로만 한다.**

- DB를 바꾸는 근거는 기준 2~4다. 0단계와 3단계의 활성 소속 규칙을 모두 DB 제약으로 걸 수 있고, 마이그레이션 실패가 안전하며, 2단계 의미 검색을 같은 DB에서 처리한다. 옮길 데이터가 없어 지금이 전환 비용이 가장 작은 시점이다. 개발자가 써 본 DB라는 점은 보조 근거다.
- [리빌드 초기 설계안](README.md#용어)은 PostgreSQL을 고른 근거로 `SKIP LOCKED`를 들었다. MySQL 8도 지원하므로 근거에서 뺀다.
- Flyway를 쓰고, 운영과 로컬 모두 `ddl-auto=validate`로 둔다. 엔티티와 스키마가 다르면 서버가 시작하지 않는다. Liquibase의 DB 독립성은 PostgreSQL로 정한 지금 필요하지 않다.
- 조회는 JPA로 통일하고 MyBatis는 쓰지 않는다. 목록 조회는 fetch join이나 DTO projection으로 한 번에 가져온다. QueryDSL은 JPA만으로 조회 코드가 감당하기 어려워질 때 도입하며, 그때는 관리가 이어지고 있는 OpenFeign 포크를 쓴다.
- DB를 어디서 실행할지(관리형 서비스 여부)는 ADR 0017에서 정한다.

## 결과

- 얻는 것: 빈 DB에서 마이그레이션만으로 스키마를 재현한다. 서비스 규칙 일부를 DB가 보장한다. 2단계에 벡터 DB를 따로 두지 않는다.
- 잃는 것: 마이그레이션 SQL을 직접 작성한다. 조건이 아주 많은 조회는 JPQL로 쓰기 번거로울 수 있다.
- 후속 작업: 테이블 설계는 [03-architecture.md](../03-architecture.md)와 구현 단계에서 한다. 여러 가족 소속으로 확장할 때 DB와 API를 크게 바꾸지 않도록, 가족 안의 활동(답변, 반응 등)을 사용자가 아니라 구성원(Member) 기준으로 저장하는 원칙도 03에서 정한다.

## 검증

assertion:

- 빈 PostgreSQL에 Flyway 마이그레이션을 적용하면 운영과 같은 스키마가 만들어지고, `ddl-auto=validate`로 서버가 시작된다.
- (0단계) 한 사용자가 활성 상태로 두 가족에 속하는 데이터를 넣으면 DB가 거부한다.
- (0단계) 가족을 나간 기록이 있는 사용자도 새 가족에 활성 상태로 들어갈 수 있다.
- (3단계) 인덱스를 바꾸는 마이그레이션을 적용한 뒤에는, 한 사용자가 여러 가족에 활성 상태로 속할 수 있고 같은 가족에 활성 상태로 두 번 속하는 데이터는 거부된다.
- 답변 목록 API는 답변 수와 관계없이 일정한 횟수의 쿼리로 응답한다(쿼리 수를 세는 테스트로 확인).
