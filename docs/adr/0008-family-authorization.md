# 0008. 가족 단위 권한 확인

- 상태: 채택
- 날짜: 2026-11-20
- 관련 문제: P-13 ([01-legacy-analysis.md](../01-legacy-analysis.md))

## 맥락

기존 BE는 목록 조회에서는 로그인한 사용자의 가족으로 결과를 걸렀지만, ID로 단건을 조회하거나 쓰는 API 대부분은 같은 가족인지 확인하지 않았다. 답변 상세, 댓글 조회와 작성, 쪽지 읽기가 그랬고, 사진 목록 쿼리는 모든 가족의 사진을 반환했다(P-13). 권한 확인을 서비스 메서드마다 직접 작성하다 보니 빠진 곳이 생겼다.

이 서비스에서 가족의 기록이 가족 밖으로 새는 것은 가장 큰 사고다. 리빌드의 문제 정의에도 "기록은 가족 안에서만 보인다"가 들어 있다([02-domain-and-problem.md](../02-domain-and-problem.md) 5장).

## 판단 기준

1. 권한 확인을 빠뜨린 API가 생기기 어렵다
2. 빠뜨린 API가 있으면 테스트에서 드러난다
3. 다른 가족 데이터의 존재 여부도 드러나지 않는다
4. 나중에 한 사용자가 여러 가족에 속하도록 확장할 수 있다(3단계)
5. 1인 개발로 구현하고 유지할 수 있다

## 후보

### A. 서비스 메서드마다 직접 확인 (기존)

- 장점: 단순하다.
- 단점: 새 API를 만들 때마다 기억해서 넣어야 해 빠뜨리기 쉽다(기준 1). 기존 문제가 이 방식에서 생겼다.

### B. 경로에 가족을 명시하고, 공통 계층에서 구성원 여부를 확인

가족 단위 리소스는 모두 `/families/{familyId}/...` 경로 아래 둔다. 공통 계층(Spring Security 또는 인터셉터)이 요청한 사용자가 그 가족의 활성 구성원인지 먼저 확인한다. 조회 쿼리에는 항상 `familyId` 조건을 넣는다.

- 장점: 경로 규칙만 지키면 확인이 자동으로 붙는다(기준 1). 경로에 가족이 있어 여러 가족 소속으로 확장하기 쉽다(기준 4).
- 단점: 경로의 `familyId`와 리소스가 실제로 속한 가족이 다른 경우(예: 우리 가족 경로로 다른 가족 답변 ID를 요청)를 쿼리 조건으로 함께 막아야 한다.

### C. DB 행 수준 보안 (PostgreSQL Row-Level Security)

DB가 요청마다 현재 사용자의 가족에 속한 행만 보여주게 한다.

- 장점: 애플리케이션 코드에서 빠뜨려도 DB가 막는다.
- 단점: 요청마다 DB 세션에 사용자 정보를 설정해야 하고, JPA와 커넥션 풀 환경에서 다루기 까다롭다(기준 5). 디버깅이 어려워진다.

## 결정

**B를 채택한다.** C는 B로 운영해 본 뒤 필요하면 검토할 개선 후보로 둔다.

- 가족 단위 리소스는 모두 `/families/{familyId}/...` 경로 아래 둔다.
- 공통 계층에서 요청한 사용자가 경로의 가족에 속한 활성 구성원인지 확인한다. 아니면 요청을 거부한다.
- 단건 조회와 수정·삭제 쿼리는 리소스 ID와 함께 `familyId`를 조건으로 넣는다. 우리 가족 경로로 다른 가족의 리소스 ID를 요청하면 찾지 못한다.
- 다른 가족의 리소스와 존재하지 않는 리소스는 같은 응답(404)을 돌려준다. 응답으로 다른 가족 데이터의 존재 여부를 알 수 없게 한다.
- 가족 안의 활동(답변, 반응, 댓글)은 사용자(User)가 아니라 가족 구성원(Member) 기준으로 저장한다. 인증은 User, 가족 리소스 권한은 Member로 판단한다.
- 작성자만 할 수 있는 일(내 답변 수정·삭제)은 구성원 확인 위에 작성자 확인을 더한다.
- S3의 영상과 썸네일도 같은 확인을 통과한 요청에만 presigned URL을 발급한다([ADR 0003](0003-video-upload.md)).

## 결과

- 얻는 것: 경로 규칙을 따르면 가족 확인이 자동으로 붙는다. 여러 가족 소속으로 확장할 때 API를 바꾸지 않아도 된다.
- 잃는 것: 모든 쿼리에 `familyId` 조건을 넣는 규칙을 지켜야 한다. 규칙 위반은 아래 테스트로 잡는다.
- 후속 작업: 가족 경로 밖에 둘 API 목록(로그인, 가입, 초대 코드 확인 등)을 정한다.

## 검증

assertion:

- 가족 단위 API 전체에 대해, 다른 가족의 구성원이 요청하면 404를 받는다. 테스트는 등록된 API 목록을 자동으로 순회해, 새 API가 추가되면 함께 검사된다.
- 우리 가족 경로에 다른 가족의 리소스 ID를 넣어 요청하면 404를 받는다.
- 가족을 나간 구성원은 그 가족의 리소스에 접근할 수 없다.
- 작성자가 아닌 구성원은 다른 사람의 답변을 수정하거나 삭제할 수 없다.
