# 0020. 메일 발송 작업의 인증 코드 원문 보관

- 상태: 채택
- 날짜: 2026-11-27
- 관련 문제: P-15 ([01-legacy-analysis.md](../01-legacy-analysis.md))
- 바꾸는 결정: [ADR 0009](0009-auth-token.md)의 세부 규칙 중 "비밀번호 재설정"의 "DB에 해시로 저장한다"

## 맥락

[ADR 0009](0009-auth-token.md)는 비밀번호 재설정 코드를 "DB에 해시로 저장한다"고 정했고, 가입 인증 코드도 같은 규칙을 따른다([03-architecture.md](../03-architecture.md) 8장). 기존 프로젝트는 코드를 메모리에 두고 시도 횟수 제한이 없었다(P-15).

[ADR 0018](0018-email-delivery.md)은 메일을 요청 트랜잭션에서 발송 작업으로 저장하고, 커밋 직후 보낸 뒤 실패하면 스케줄러가 다시 보내도록 정했다. 다시 보내려면 메일 본문이 있어야 하고, 본문에는 코드 원문이 들어간다. 두 결정을 함께 따르면 코드 원문이 발송 작업 표(`mail_jobs`)에 잠시 남는다. 가입·로그인 PR 2를 만들면서 이 충돌을 발견했고, 2026-11-26에 계획 문서에만 기록한 채 병합했다. 이 ADR은 그 판단을 결정으로 남긴다.

## 판단 기준

1. DB가 새도 쓸 수 있는 코드가 거의 남지 않는다
2. 메일 발송이 일시적으로 실패해도 재시도해 결국 보낸다(ADR 0018의 검증)
3. 구현이 단순하다

## 후보

### A. 코드 해시만 저장하고, 재시도하지 않는다

- 장점: ADR 0009를 그대로 지킨다.
- 단점: 발송이 일시적으로 실패하면 메일이 가지 않는다. 사용자가 코드를 다시 요청해야 하고, 요청 횟수 제한에 걸릴 수 있다(기준 2).

### B. 재시도할 때 코드를 새로 만들어 보낸다

- 장점: 원문을 저장하지 않는다.
- 단점: 앞서 보낸 메일이 늦게 도착하면 사용자가 무효가 된 코드를 입력하게 된다. 발송 작업이 코드를 다시 만드는 책임까지 져서 메일 발송과 인증이 얽힌다(기준 3).

### C. 본문(코드 원문 포함)을 발송 작업에 저장하고, 보낸 뒤나 만료되면 지운다

- 장점: ADR 0018의 재시도를 그대로 쓴다(기준 2). 원문이 남는 시간은 보내기 전까지이고, 길어도 코드가 만료되는 10분이다(기준 1).
- 단점: 그 사이에 DB가 새면 아직 보내지 못한 코드가 드러난다.

## 결정

**C를 채택한다.**

- 원문이 남는 것은 보내기 전, 최대 10분이고, 그 코드는 만료와 5회 틀림 제한이 그대로 걸린다. DB가 새는 순간과 겹쳐야 피해가 생긴다.
- 코드 확인은 여전히 `email_codes`의 해시로만 한다. 발송 작업의 본문은 확인에 쓰지 않는다.
- 보내면 바로, 보내지 못하고 만료되면 그때 본문을 지운다. DB 제약으로 대기 중이 아닌 작업에는 본문이 남지 않게 한다(`CHECK (status = 'PENDING' OR body IS NULL)`).

## 결과

- 얻는 것: 메일 발송의 재시도와 코드 해시 저장을 함께 쓴다.
- 잃는 것: 보내기 전 최대 10분 동안 코드 원문이 DB에 있다.
- 후속 작업: 없음

## 검증

assertion:

- 보낸 메일과 보내지 못하고 만료된 메일의 본문은 DB에 남지 않는다.
